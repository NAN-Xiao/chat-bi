# 工作空间待审核通知头像红点设计

## 背景

工作空间拥有者或管理员收到当前工作空间的待审核申请时，审核入口内已有数量提示，但全局顶部头像没有提醒。用户需要进入管理页面后才能发现待处理事项。

## 目标

- 当前工作空间存在待审核申请时，在全局顶部头像右上角显示纯红点。
- 仅工作空间角色为 `owner` 或 `admin` 的用户显示该红点。
- 红点不展示数量，不改变头像点击、菜单展开或现有导航行为。
- 切换工作空间后，红点必须反映新工作空间的待审核状态。

## 非目标

- 不建设通用消息中心或全局通知 Store。
- 不引入轮询、WebSocket 或服务端推送。
- 不改变工作空间审核流程、权限规则或接口协议。
- 不为普通成员、无工作空间用户、平台管理员或平台工作空间代理展示该红点。

## 方案选择

### 方案一：头像组件直接请求通知接口

改动较少，但会让通用 `UserAvatar` 组件依赖工作空间权限和审核业务，不利于复用与维护。

### 方案二：布局用户组件管理审核状态（采用）

由 `frontend/src/components/layout/Person.vue` 判断当前角色、加载当前工作空间待审核申请，并在头像外层渲染红点。业务状态留在布局层，通用头像组件保持无业务依赖。

### 方案三：建立全局通知 Store

适合未来消息中心、实时通知和多类未读消息，但当前需求单一，引入额外状态同步与生命周期管理属于过度设计。

## 详细设计

### 数据来源

复用现有 `tenantApi.tenantApplications('pending')` 接口。该接口按当前工作空间上下文返回待审核申请列表，不新增后端接口。

### 权限与显示条件

复用 `canManageWorkspaceRole` 判断当前工作空间角色。只有同时满足以下条件才显示红点：

1. 当前角色可管理工作空间，即 `owner` 或 `admin`；
2. 当前存在有效工作空间上下文；
3. 当前不是平台管理员或平台工作空间代理上下文；
4. 待审核申请数量大于零。

普通成员、无工作空间用户、请求失败或待审核数量为零时不显示红点。

### 生命周期

- `Person.vue` 挂载后，在满足管理角色条件时加载待审核申请。
- 当前工作空间标识或角色变化时重新加载。
- 角色失去管理权限或工作空间上下文被清空时，立即清空本地待审核数量。
- 使用请求序号或等价保护，避免快速切换工作空间时旧请求覆盖新状态。

### 视觉与交互

- 在头像外增加相对定位容器，红点绝对定位于右上角。
- 红点为纯视觉提示，不显示数字，并设置无障碍文本说明。
- 红点不拦截鼠标事件，头像点击区域和下拉菜单行为保持不变。
- 样式限定在 `Person.vue`，避免影响其他 `UserAvatar` 使用位置。

### 异常处理

接口失败时将待审核状态视为未知并隐藏红点，不弹出错误消息、不阻塞布局渲染。后续工作空间切换或组件重新挂载时可再次请求。

## 测试策略

- 提取可独立测试的显示判断函数，覆盖拥有者、管理员、普通成员、无工作空间和不同待审核数量。
- 覆盖平台管理员、平台工作空间代理不显示红点。
- 覆盖只有业务工作空间管理角色且数量大于零时返回显示状态。
- 运行新增前端单元测试与 TypeScript 构建检查。

## 风险与边界

- 当前设计不是实时推送；用户停留在同一页面期间新增申请不会立即出现，需依赖重新挂载或工作空间切换刷新。
- 若后续要求实时更新，应升级为统一通知状态管理，并通过轮询、事件总线或服务端推送更新，不应继续在头像组件内堆叠请求逻辑。

## 验收标准

1. 空间拥有者或管理员在当前空间存在待审核申请时，顶部头像右上角显示红点。
2. 待审核数量为零时不显示红点。
3. 普通成员、平台管理员和平台工作空间代理不显示该审核红点。
4. 切换空间后红点状态与新空间一致，旧请求不会污染新空间状态。
5. 点击头像和原有菜单交互不受影响。
