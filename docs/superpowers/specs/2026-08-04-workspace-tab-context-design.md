# AI 看板标签页级工作空间上下文设计

状态：已确认

日期：2026-08-04

## 背景

AI 看板在回答过程中快速切换工作空间时，会同时出现“切换成功”和
`Datasource access is required`。后端日志确认，失败请求来自 Agent / Data Skills
列表接口：请求携带了新工作空间租户 ID，但查询参数仍是旧工作空间的数据源 ID。

当前实现存在三个相互叠加的竞态：

1. 当前租户保存在 `localStorage`，同源标签页共享，任一标签页切换都会改变其他标签页后续请求的租户头。
2. Axios 请求拦截器异步执行时才读取当前租户，调用方已经构造好的旧数据源参数可能与稍后读取的新租户组合。
3. 所有成功响应都会根据租户响应头修改当前工作空间，旧请求晚返回时可以覆盖刚完成的切换。

后端 403 是正确的租户隔离保护，不应放宽。

## 目标

- 每个浏览器标签页可以独立停留在不同工作空间。
- 同一标签页快速执行 `A -> B -> C` 时，只允许最后一次切换提交。
- 工作空间切换期间，不发送“新租户 + 旧数据源”的组合请求。
- 旧工作空间的晚到响应不得修改新工作空间状态或 UI。
- AI 后台任务可以继续完成；返回原工作空间后仍能读取已完成结果。
- 保持后端租户和数据源权限校验不变。

## 非目标

- 不修改数据库结构、任务 Worker、AI 模型调用或 SQL 生成流程。
- 不允许跨工作空间读取聊天、数据源、Agent、Data Skills 或看板数据。
- 不让不同标签页共享当前工作空间选择。
- 不通过重试 403、忽略权限错误或自动替换数据源掩盖配置不一致。

## 设计决策

### 1. 拆分身份状态和工作空间状态

登录 Token、用户 ID、账号等身份状态继续保存在 `localStorage`，保持登录会话跨标签页共享。

只将当前工作空间 ID 保存在 `sessionStorage`。工作空间名称、角色和状态由当前标签页的
Pinia 用户 Store 持有，并在刷新时通过当前工作空间 ID 重新请求用户信息恢复。现有
`localStorage` 中的 `user.tenantId`、`user.tenantName`、`user.tenantRole`、
`user.workspaceRole`、`user.hasWorkspace` 和 `user.workspaceStatus` 不再作为运行时来源，
启动时只做显式清理，不做静默回退。

平台管理员的工作空间代理上下文本来就使用 `sessionStorage`，新上下文模块必须保留其
专用请求头和优先级，不将普通工作空间状态混入代理状态。

### 2. 标签页级 WorkspaceContext

新增一个前端工作空间上下文模块，作为当前标签页租户选择的唯一所有者。它维护：

- `activeTenantId`：已提交且可用于普通业务请求的租户 ID。
- `pendingTenantId`：正在验证的切换目标。
- `phase`：`bootstrapping`、`ready` 或 `switching`。
- `epoch`：每次开始切换或重新初始化时递增的上下文版本。
- `switchId`：每次切换的唯一序号，用于保证 latest-wins。

每个切换事务还保存不可变的原工作空间快照，包括租户 ID、用户 Store 中的工作空间字段和
原数据源 ID。该快照只用于当前最新事务失败时回滚，不写入共享存储。

用户 Store 负责用户展示信息和权限派生，不再自行决定请求使用哪个租户。请求层、路由层、
工作空间选择器和业务页面都通过 WorkspaceContext 读取活动租户。

### 3. 原子切换事务

工作空间切换按以下顺序执行：

1. `beginSwitch(targetTenantId)` 递增 `epoch` 和 `switchId`，进入 `switching`。
2. 广播 `changing` 事件；页面停止轮询和流式读取，清空当前聊天及数据源内存状态，但不删除其他租户的持久偏好。
3. 使用显式目标租户头请求用户信息。该请求标记为“切换验证请求”，不使用活动租户默认值，
   并且只返回待验证 DTO，不直接修改用户 Store。现有 `info()` 需要拆分为纯请求和显式应用两步。
4. 验证响应租户必须等于目标租户。后端若回退到其他租户，视为目标不可用，不得静默提交。
5. 只有返回时仍是最新 `switchId` 的事务才能提交。较早事务的成功或失败结果均被忽略。
6. 提交活动租户到 WorkspaceContext 和 `sessionStorage`，再将响应中的工作空间信息应用到用户 Store。
7. 强制加载新租户可访问的数据源；完成后进入 `ready`，广播 `changed`，重新加载聊天列表、Agent 和 Data Skills。接口成功但列表为空表示该工作空间没有绑定数据源，仍属于有效的 ready 状态。
8. 目标验证失败或数据源接口请求失败时回滚原活动租户和用户 Store，重新加载原租户数据源，进入 `ready` 并显示明确错误。

快速切换不依赖禁用整个工作空间菜单；latest-wins 保证最终状态确定。当前目标可显示加载态，
重复点击同一目标不启动新事务。

### 4. 请求上下文快照

普通 Axios 请求必须在进入公共 `request()` 方法的同步时刻捕获：

```ts
type WorkspaceRequestSnapshot = {
  tenantId: string
  epoch: number
  phase: 'bootstrapping' | 'ready' | 'switching'
}
```

快照写入请求配置的内部元数据，并立即生成 `X-SHUZHI-TENANT-ID`。异步请求拦截器只能使用
已捕获的请求头，不得再次从存储读取当前租户。`fetchStream()` 也必须在任何 `await` 之前
捕获同一快照。

普通工作空间请求只有在捕获时为 `ready` 才能把结果交给调用方。切换验证、登录初始化、
平台代理等特殊请求使用显式策略，不走普通请求的活动租户推断。

已经提交到旧工作空间的写操作或 AI 任务仍由后端按其捕获的旧租户处理；切换后的页面不再
消费其响应。该行为避免把已经开始的任务错误迁移到新工作空间。

### 5. 响应校验和过期结果

响应拦截器不再根据任意响应头调用 `setTenant()`。它只做以下校验：

- 响应租户必须与请求快照租户一致。
- 请求快照的 `epoch` 必须仍是当前活动版本。
- 普通请求捕获时和返回时都必须处于可消费的 `ready` 上下文。

不满足条件的响应转换为可识别的 `WorkspaceContextStaleError`，不显示通用错误 Toast，
也不更新 Store 或组件业务数据。工作空间切换事件负责清理旧页面 loading；选择器等可能并发
重载的组件只允许当前加载序号在 `finally` 中修改自己的 loading，避免旧请求清除新请求的加载态。
真正来自当前上下文的 401/403 继续走正常错误处理。

刷新初始化是唯一允许根据服务器响应建立活动租户的普通登录路径。若 `sessionStorage` 中的
租户已失效而后端返回其他租户，前端必须明确提示原工作空间不可用，再提交服务器解析出的
可用工作空间；不能无提示回退。

### 6. Agent、Data Skills 和短期缓存

AgentSelector 和 DataSkillSelector 在工作空间不是 `ready` 或数据源为空时不加载。它们的
watcher 必须监听 ready 状态，在切换完成后主动重新加载。

每个选择器维护自己的加载序号。只有最新序号且租户、数据源仍匹配的结果可以写入列表，
旧结果不得清空新列表或清除用户选择。

`requestDedupe` 的 Agent / Data Skills 缓存键必须包含租户 ID、数据源 ID 和目标作用域。
切换开始时清除这两类短期缓存，避免未完成 Promise 被新上下文复用。

### 7. 页面和路由行为

AI 看板继续在 `changing` 时停止当前视图的轮询、流式读取和推荐问题加载，并重置当前聊天。
`changed` 只能在新数据源加载完成后发出。输入框、新建对话、重新生成、Agent 和 Data Skills
入口在 `switching` 阶段保持禁用。

路由初始化先恢复当前标签页的 WorkspaceContext，再调用用户信息接口和动态路由生成。
工作空间管理页返回业务页时继续使用现有 `workspaceAdminContext`，但恢复操作必须走同一切换事务。

同一工作空间下当前对话的 `sessionStorage` 键继续包含用户、租户和数据源边界。不同标签页可有
不同当前对话，不相互覆盖。

## 异常处理

- 目标工作空间无权限、已禁用或不存在：切换失败并恢复原空间；显示明确提示。
- 切换过程中再次切换：旧事务结果静默丢弃，最后一次事务负责最终状态。
- 数据源接口请求失败：回滚原工作空间并恢复原数据源；显示目标工作空间加载失败。成功返回空列表不回滚，而是进入无数据源的 ready 状态。
- 旧请求返回：静默丢弃，不显示 403/取消错误，不修改新页面。
- 当前上下文真实 403：保留后端错误并本地化展示，不能当作过期请求吞掉。
- 刷新时保存的工作空间失效：明确提示后切换到服务器解析的可用空间。

## 测试设计

### 单元测试

- 两个模拟标签页拥有独立 `sessionStorage` 工作空间，Token 仍共享。
- 请求在调用入口捕获租户 A；即使拦截器执行前切到 B，请求头仍为 A。
- A 的响应在 B 提交后不能修改 Store 或显示错误。
- `A -> B -> C` 乱序完成时只提交 C。
- B 切换失败时恢复 A，且旧 B 响应随后到达仍被忽略。
- Agent / Data Skills 在 switching 不发请求，在 ready 后只应用最新加载结果。
- Agent / Data Skills 缓存键包含租户和数据源边界。

### 集成回归

- 单标签页在 AI 回答过程中连续切换工作空间，不出现 `Datasource access is required`。
- 两个标签页分别停留在修仙和 Flam，同时提问时请求租户与数据源各自正确。
- 切回原工作空间后可以读取切换期间完成的 AI 任务结果。
- 刷新两个标签页后分别恢复自己的工作空间。
- 工作空间权限被收回、工作空间禁用、数据源加载失败时状态可恢复且提示明确。
- 平台管理员、平台工作空间代理、普通成员和工作空间管理员路径保持可用。
- 登录、退出、动态路由、看板、分析助手、Agent 和 Data Skills 页面完成基础冒烟测试。

## 实施范围

预计主要修改以下前端边界：

- 工作空间上下文和存储封装。
- 用户 Store 的初始化、应用用户信息和切换事务。
- Axios 普通请求、流式请求及响应校验。
- 工作空间选择器和路由恢复流程。
- AI 看板工作空间事件处理。
- AgentSelector、DataSkillSelector 和它们的短期请求缓存键。
- 上述行为的单元与集成回归测试。

后端只作为现有权限行为的验证对象，默认不改代码。

## 验收标准

- 两个标签页可以长期停留在不同工作空间且互不改变对方的请求租户。
- 任意工作空间业务请求的租户头与其数据源、对话和缓存上下文一致。
- 快速切换和旧响应乱序均不能产生跨租户 UI 状态、错误 Toast 或状态回滚。
- 当前上下文的真实权限错误仍然可见，后端租户隔离校验保持有效。
- 既有工作空间管理、平台代理和刷新恢复路径通过回归测试。
