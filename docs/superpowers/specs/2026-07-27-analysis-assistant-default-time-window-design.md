# 综合分析助手默认时间窗口设计

## 背景

综合分析助手当前能够从用户问题、Data Skill、工作空间数据字典和数据库 Schema 生成多角度分析计划，但当用户没有说明时间范围时，没有统一的默认时间策略。模型可能生成无时间条件的事实表查询，也可能在不同分析块中使用不同的时间窗口。

本设计为 `/analysis-assistant/chat` 增加统一的时间语义：当用户和 Data Skill 都没有明确时间规则时，以当前分析主题的最大业务日期为结束日，默认分析含结束日在内的最近 14 个自然日。

## 目标

- 用户明确时间、Data Skill 明确业务时间窗口和平台默认时间之间具有确定优先级。
- 默认窗口以最大业务日期为锚点，而不是系统当前日期。
- 分析计划、SQL、图表标题、分块总结和最终结论使用同一时间范围。
- 提示词主动引导模型生成正确时间条件，后端在执行前进行结构化校验和安全补齐。
- 无法安全补齐单个分析块时不中断整次分析，同时不执行无时间边界的事实表 SQL。
- 用户能够从执行轨迹看到系统最终采用的时间范围及降级信息。

## 非目标

- 不继承当前看板或页面筛选器的时间范围。
- 不改变看板 SQL、Smart Q&A 或 `/analysis-assistant/report-interpretation` 的时间语义。
- 不为所有 Data Skill 推断或迁移默认时间窗口。
- 不静默选择 Schema 中的第一个日期字段。
- 不使用系统日期作为最大业务日期探测失败后的回退值。
- 不通过动态 `MAX(date)` CTE 或 `CROSS JOIN bounds` 生成事实查询的时间边界。

## 时间策略优先级

时间策略按以下优先级解析：

1. 用户本轮或最近对话明确给出的时间范围。
2. 当前命中的 Data Skill 明确声明的业务时间窗口。
3. 平台默认的最近 14 个自然日。

用户明确时间始终优先。Data Skill 的结构化时间声明可以覆盖平台默认值，但 Skill 中示例 SQL 恰好使用某个日期范围，不视为明确声明。

默认 14 天按包含结束日计算：

```text
end_date = 最大业务日期
start_date = end_date - 13 天
```

例如最大业务日期是 `2026-07-26`，默认范围为 `2026-07-13` 至 `2026-07-26`。

## 日期语言识别

### 完整日期和相对时间

以下表达视为用户已经明确时间，不应用默认 14 天：

- 绝对范围：`2026-07-01 到 2026-07-10`。
- 相对范围：`最近 7 天`、`近两周`、`昨天`、`本月`。
- 开放范围：`7 月 14 日之后`、`从 7 月 14 日开始`。

### 不完整日期

`14日之后`、`从14号开始` 等只有日、没有年月的表达，也视为明确时间条件。年月按以下优先级补全：

1. 本轮问题中明确的年月。
2. 最近对话中明确且仍适用于当前问题的年月。
3. 最大业务日期对应的最近一次、不晚于最大业务日期的该月日。

例如最大业务日期为 `2026-07-26`：

- `14日之后` 解释为 `2026-07-15` 至 `2026-07-26`。
- `从14号开始` 解释为 `2026-07-14` 至 `2026-07-26`。

如果最大业务日期为 `2026-07-10`，当月 14 日尚未发生，则最近有效的 14 日是 `2026-06-14`：

- `14日之后` 解释为 `2026-06-15` 至 `2026-07-10`。
- `从14号开始` 解释为 `2026-06-14` 至 `2026-07-10`。

包含关系必须确定：

- `14日之后` 使用 `>`，不包含 14 日。
- `从14号开始`、`14日起`、`14日及以后` 使用 `>=`，包含 14 日。

解析结果必须通过执行轨迹展示，用户后续纠正年月时，以新输入重新解析并分析。

## Data Skill 时间声明

为避免从 Markdown 示例 SQL 猜测规则，Data Skill 仅通过结构化声明覆盖平台默认窗口。建议使用可选注释：

```html
<!-- data-skill-analysis-time:{"window_days":30,"anchor":"latest_available"} -->
```

第一版仅支持：

- `window_days`：正整数自然日窗口。
- `anchor`：固定为 `latest_available`。

声明解析失败、值越界或与权限和 Schema 冲突时忽略该声明，并记录可见的时间策略警告；不得从示例 SQL 自动推导替代值。

## 架构

新增独立模块 `backend/apps/analysis_assistant/service/analysis_time_policy.py`，避免继续扩大 `analysis_assistant.py`。模块负责时间意图识别、策略解析、日期补全和时间策略描述，不负责执行任意 SQL。

核心对象 `AnalysisTimePolicy` 包含：

```text
source          USER / DATA_SKILL / DEFAULT_14_DAYS
window_days     可选窗口天数
anchor_date     最大业务日期或用户确定的结束日期
start_date      已确定的开始日期
end_date        已确定的结束日期
start_inclusive 开始日期是否包含
end_inclusive   结束日期是否包含
anchor_table    作为业务日期锚点的授权表
anchor_field    经过 Schema 验证的时间字段
description     用于轨迹、快照和最终解释
```

`AnalysisTimePolicy` 不保存跨租户对象，不允许根据字段名称相似度静默替换字段。

## 数据流

1. `/analysis-assistant/chat` 获取本次问题、最近对话、当前数据源、Data Skills 和业务 Schema。
2. 时间策略模块识别用户时间表达，并读取 Data Skill 的结构化时间声明。
3. 如果需要最大业务日期，先执行锚点选择阶段；该阶段只返回统一的 `anchor_table` 和 `anchor_field`，不返回也不执行分析 SQL。
4. 后端验证表、字段、字段类型和当前用户权限。
5. 后端通过现有受权限控制的查询执行器执行轻量探测：

   ```sql
   SELECT business_date
   FROM authorized_table
   WHERE business_date IS NOT NULL
   ORDER BY business_date DESC
   LIMIT 1
   ```

6. 探测结果按租户、数据源、表、字段和权限相关上下文短时缓存。一次请求中相同锚点只探测一次。
7. 后端得到确定的起止日期，将时间策略注入分析计划提示词，使模型生成统一标题和带常量边界的 SQL。
8. SQLGlot 在执行前验证相关事实表查询是否使用已确定时间字段和范围。
9. 通过校验的 SQL 走现有 `execute_user_analysis_query_or_raise` 权限和安全执行路径。
10. 时间策略写入 `context_snapshot` 和 SSE 执行轨迹，供历史会话审计与前端展示。

### 两阶段计划契约

需要最大业务日期的请求分为两个模型阶段：

1. 锚点选择阶段：根据用户问题、Data Skill 和授权 Schema 选择一个主业务时间表和时间字段，只返回结构化锚点，不生成可执行分析 SQL。
2. 可执行计划阶段：后端完成锚点探测并计算起止日期后，把确定的时间策略注入提示词，再生成包含 SQL 的完整分析计划。

用户已经给出完整绝对日期，且不需要最大业务日期补全年月时，可以跳过锚点探测；可执行计划仍必须声明所使用的时间字段，供执行前校验。任何情况下都不得在时间策略尚未确定时执行事实表分析 SQL。

## 提示词约束

`PLAN_PROMPT` 和预测计划提示词需要增加以下通用规则：

- 时间策略由后端确定，模型不得重新解释或扩大范围。
- 所有相关分析块必须使用给出的起止日期和包含关系。
- SQL 必须使用具体日期常量，不能在事实查询中通过动态最大日期 CTE 计算边界。
- 图表标题、分析说明和最终结论必须说明实际使用的时间范围。
- 维表或配置表没有适用时间字段时，不得伪造时间条件。

提示词是主动引导层，不能代替执行前校验。

## SQL 校验与补齐

后端校验必须基于 SQLGlot AST 和已经验证的表、字段及日期常量：

- 检查相关事实表是否存在有效的下界和上界。
- 检查边界是否与 `AnalysisTimePolicy` 一致。
- 检查多分析块是否使用同一请求级时间范围。
- 检查多事实表查询的相关扫描是否分别受到常量时间条件约束。

发现缺失或冲突时按以下顺序处理：

1. 携带已确定表、字段、起止日期和包含关系重新生成当前 SQL。
2. 如果 SQLGlot 能唯一定位目标扫描和时间字段，执行确定性 AST 补齐。
3. 如果结构复杂或目标不唯一，跳过当前数据块，不执行该 SQL。

不得采用字符串拼接、首字段替代、近似字段匹配或无提示的系统日期回退。

## 非阻断降级

非阻断指不因单个时间问题终止整次综合分析，不代表允许执行无边界 SQL。

- 单个数据块无法修复：标记该块未完成，继续执行其他数据块。
- 部分数据块成功：基于成功数据块生成最终结论，并明确未覆盖角度。
- 所有数据块无法执行：SSE 仍返回正常的 `final` 和 `finish`，说明当前数据源缺少可确认的业务时间字段，不能形成有数据支撑的结论。
- 最大业务日期探测失败：仅允许读取完全相同租户、数据源、表、字段和权限上下文下的有效短期缓存；没有缓存时按上述规则降级。

不向用户暴露数据库异常堆栈、具体无权限字段或内部权限规则。

## 用户反馈

沿用现有执行轨迹，不增加弹窗或新的前端配置控件：

```text
问题未指定时间，正在确认最大业务日期。
已采用默认时间范围：2026-07-13 至 2026-07-26。
已将“14日之后”解释为 2026-07-15 至 2026-07-26。
“渠道结构”无法确认有效时间字段，本次结论未包含该角度。
```

历史会话的 `agentContextSnapshot.business_context` 增加不含敏感值的时间策略元数据，包括来源、起止日期、锚点表字段摘要和策略状态。

## 测试设计

### 时间语义单元测试

- 没有用户时间和 Skill 时间声明时使用默认 14 天。
- `最近7天`、绝对日期范围、昨天和本月不触发默认 14 天。
- Data Skill 有合法结构化声明时覆盖默认值。
- Skill 仅在示例 SQL 中出现 30 天时不覆盖默认值。
- `14日之后` 与 `从14号开始` 的包含关系正确。
- 最大业务日期早于当月 14 日时选择最近已经发生的 14 日。
- 用户后续明确年月时覆盖此前补全年月。

### SQL 安全测试

- 事实表 SQL 使用具体日期常量。
- 不生成动态 `MAX(date)` 或 `CROSS JOIN bounds` 时间边界。
- SQLGlot 仅在表和字段唯一确定时补齐条件。
- 多分析块使用完全相同的请求级起止日期。
- 多事实表查询的相关扫描分别具备常量时间条件。
- 无法确认时间字段时不选择第一个日期字段，不执行无边界 SQL。

### 降级和权限测试

- 单个数据块无法修复时其他数据块继续执行。
- 所有数据块失败时仍返回 `final` 和 `finish`，不返回接口级异常。
- 最大业务日期探测走现有用户权限执行器。
- 日期缓存包含租户、数据源、表、字段和权限上下文边界。
- 无权限表或字段不能用于日期探测和 SQL 补齐。

### 回归测试

- `/analysis-assistant/chat` 应用新策略。
- `/analysis-assistant/report-interpretation` 行为不变。
- Smart Q&A 和看板 SQL 生成行为不变。
- 用户明确时间和现有 Data Skill 业务口径不被默认 14 天覆盖。

## 验收标准

当最大业务日期为 `2026-07-26`，用户输入 `分析一下渠道收入变化`：

- 执行轨迹显示默认时间范围为 `2026-07-13` 至 `2026-07-26`。
- 分析计划、所有相关 SQL、图表标题、分块总结和最终结论使用同一范围。
- 事实查询使用日期常量，具备可验证的分区裁剪条件。
- 无法安全补齐的单个分析块不会中断其他分析块。
- 看板、Smart Q&A 和报表解读行为保持不变。

当用户输入 `分析14日之后的数据`：

- 不应用默认 14 天。
- 系统按最近有效月份解释年月。
- `之后` 不包含 14 日。
- 执行轨迹显示最终解析出的完整日期范围。

当用户输入 `从14号开始分析`：

- 不应用默认 14 天。
- 开始日期包含 14 日。
- 执行轨迹显示最终解析出的完整日期范围。

## 风险与控制

- 日期字段选择错误：仅接受授权 Schema 中类型有效且由计划明确声明的字段；不做相似字段替换。
- 最大日期探测性能：使用排序取首行、短期缓存和每请求去重；实现阶段需对目标数据源执行计划进行验证。
- 方言差异：日期常量和 AST 输出通过现有 SQLGlot 方言配置生成，不硬编码 PostgreSQL 语法到所有数据源。
- Skill 规则漂移：只解析结构化时间声明，非法声明产生可见警告，不从示例 SQL 推断。
- 部分结果误导：最终回答必须列出未完成的数据块，结论只能基于成功返回的数据。
