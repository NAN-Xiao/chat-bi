# 事件参数来源字段修复设计

## 背景

First Zombie 当前工作空间的事件参数配置已被错误写入：170 个事件下的 755 个属性全部使用 `source_field=ext`。其中 `ServerPayLog.money` 等已验证字段的真实 JSON 宿主列是 `personal`。根因是“事件参数对照”Excel 导入逻辑在来源字段缺失时静默回退到 `ext`，后续导出又忠实输出了已经污染的配置。

## 目标

1. 移除事件参数导入时的静默 `ext` 回退。
2. 来源字段无法从当前行、同事件上文或点号属性名确定时，拒绝该属性并给出包含 Excel 行号的明确错误。
3. 保留同一事件内紧凑行继承显式来源字段的能力。
4. 备份并修复 First Zombie 当前工作空间已经污染的事件参数配置。
5. 重新导出并验证来源字段、JSON 路径和 SQL 生成结果。

## 代码设计

`_parse_event_parameter_mapping_sheet` 只接受三类来源：当前行显式 `source_field`、同一事件前一属性的显式来源、属性名中的宿主前缀（例如 `personal.money`）。不再使用任何默认 JSON 宿主列。

若属性名存在但仍无法确定来源字段，解析器将记录明确错误并阻止整个导入保存，避免部分跳过导致 Excel 与系统配置不一致。错误信息包含工作表名称和原始 Excel 行号，指导用户补充“数据源字段”。

现有紧凑格式继续支持：同一事件首行写 `personal`，后续属性行可以留空并继承；切换到新事件时必须重新显式给出来源字段，防止跨事件继承。

## 数据修复

修改数据库前使用仓库备份工具保存核心 PostgreSQL 配置。修复范围严格限定为 First Zombie 工作空间 `tenant_id=7477202383789887488`、数据源 `datasource_id=3`。

已验证字段直接恢复到权威配置，例如：

- `ServerPayLog.money` -> `personal` / `$.money`
- `ServerPayLog.orderId` -> `personal` / `$.orderId`
- `ServerPayLog.productid` -> `personal` / `$.productid`

其余事件属性不采用无证据的全量字符串替换。优先依据最近业务分区的事件样本确认 JSON 宿主列；无法确认的属性不伪造映射，并在修复报告中列出。修复脚本必须限定工作空间和数据源、支持事务回滚，并输出修复前后来源字段分布。

## 测试与验收

自动化测试覆盖：

- 新事件首个属性缺少来源字段时导入失败，且不会默认成 `ext`。
- 点号属性名 `personal.money` 可以推断宿主列和 JSON 路径。
- 同一事件紧凑行可以继承首行显式来源字段。
- 新事件不会继承上一事件的来源字段。
- 导出保持修复后的多宿主来源字段，不重新覆盖为 `ext`。

数据验收包括：当前配置不再出现“755 个属性全部为 ext”；`ServerPayLog` 三个权威字段均为 `personal`；重新导出的 Excel 与数据库一致；生成的充值 SQL 使用 `JSON_EXTRACT(personal, '$.money')`。

## 边界

本次不增加基于字段相似度、首列或默认 JSON 容器的兼容回退，不修改其他工作空间或数据源，也不把 First Zombie 业务字段硬编码到通用运行时路径。数据源专属修复保留在幂等种子/修复工具中。
