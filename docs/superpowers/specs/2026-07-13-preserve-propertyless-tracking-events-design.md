# 保留无属性埋点事件修复设计

## 背景与根因

First Zombie 事件字典初始化与清理流程错误地把事件条目和事件属性绑定为同一生命周期。`UserActive` 等合法事件没有专属打点属性时，属性列表为空，重建或清理过程因此把整个事件条目当成空数据移除。

事件名是工作空间内独立的业务标识，事件属性只是事件的可选子数据。事件没有属性不代表事件不存在。

## 目标

- 允许事件字典条目使用空属性列表，例如 `{"event_name": "UserActive", "properties": []}`。
- 初始化、导入、更新和属性清理后仍保留无属性事件。
- 恢复 First Zombie 当前事件字典中缺失的 `UserActive` 及其他已配置但没有属性的事件。
- 保留用户已经维护的事件说明、分类、属性和其他元数据，不用种子数据覆盖现有内容。

## 非目标

- 不从事件分组反向生成或覆盖事件字典。
- 不修改 First Zombie 的活跃用户业务口径。
- 不为无属性事件虚构属性。
- 不改变其他工作空间或数据源的事件字典。

## 方案对比

### 方案一：只补回 `UserActive`

改动最小，但没有修复生命周期错误，其他无属性事件仍可能再次丢失。

### 方案二：前端从事件分组补齐缺失事件

界面能暂时显示事件，但事件分组不是事件字典的权威来源，后端语义检索、导出和其他消费者仍会缺失该事件。

### 方案三：事件独立持久化并执行缺失项合并修复

推荐采用此方案。事件条目允许空属性列表；种子流程只补充缺失的默认事件，不覆盖已有事件；当前 First Zombie 数据执行同样的按名称合并修复。

## 数据模型与处理流程

1. 默认事件定义使用独立事件条目表示，`properties` 可以为空数组。
2. 更新或清理属性时，只改变目标事件的 `properties`，不得因为结果为空而删除事件条目。
3. First Zombie 种子执行时，以事件名为工作空间内唯一键：
   - 已存在事件保持原记录不变；
   - 缺失事件插入默认定义；
   - 不覆盖用户维护的说明、分类和属性。
4. 事件分组继续只引用事件名。分组校验确保引用的事件存在，但分组不负责创建事件。
5. 数据修复严格限定 First Zombie 的当前租户与数据源边界。

## 测试设计

- 种子默认事件中包含 `UserActive`，且允许 `properties` 为空。
- 合并时保留已有事件及其用户维护属性，只插入缺失事件。
- 属性清理后事件仍存在，属性列表为空。
- 重复执行种子结果不变，验证幂等性。
- 事件分组中的默认事件均能在事件字典中找到。
- 数据源和租户条件存在，防止跨工作空间修复。

## 验收标准

- First Zombie 事件列表重新显示 `UserActive`。
- `UserActive` 可以没有任何打点属性，并正常参与事件选择、事件分组校验和语义上下文构建。
- 现有用户维护的事件与属性没有被覆盖或删除。
- 相关后端测试通过，种子脚本重复运行不会产生重复事件或额外变更。
