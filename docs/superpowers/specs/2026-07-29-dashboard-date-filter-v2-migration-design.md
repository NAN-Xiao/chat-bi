# 看板日期筛选 V2 与存量迁移设计

## 背景

当前看板将 SQL 日期参数配置保存在 `pivot` 对象中。日期参数负责把
`{{dashboard_start_*}}` 和 `{{dashboard_end_*}}` 渲染为可执行 SQL，透视则负责时间粒度、
指标聚合和分组，两者在业务上相互独立。

现有耦合产生了两个直接问题：

1. 非透视图表保存 `pivot.enabled=false` 时，部分创建或转存链路会丢弃日期参数配置，导致 SQL
   保留占位符但缺少 `date_parameter_type`。
2. 图表刷新逻辑把大部分非权限失败视为瞬态错误。日期配置缺失后，前端保留加载态并重复请求，
   用户只能看到长期“数据加载中”，无法看到真实配置错误。

本设计面向长期运营，将日期筛选从透视配置中独立出来，引入版本化图表配置、显式存量迁移、
可退出的旧版本读取器、严格错误分类和可观测的灰度发布流程。

## 已确认决策

- 采用独立 `dateFilter` 的 V2 图表配置，不继续把日期执行配置写入 `pivot`。
- 正常图表的前端布局、控件位置、操作方式和视觉表现保持不变。
- 存量图表执行显式迁移，不在运行时静默猜测缺失配置。
- 先迁移当前工作空间，验证通过后按租户分批推广。
- 每批迁移必须支持预演、完整备份、CAS 更新、验证、审计和回滚。
- V1 读取仅作为迁移期兼容能力；V1 归零并稳定后必须关闭并删除。

## 目标

1. 日期参数和透视聚合可以独立启停；关闭透视不影响日期参数渲染。
2. 所有图表创建、编辑、AI 生成、聊天转存、复制和模板发布链路写出同一份 V2 配置。
3. 配置错误、权限错误和瞬态错误具有明确且一致的处理行为。
4. 任何图表请求最终进入可解释的终态，不再因永久错误无限加载。
5. 存量图表可以按工作空间和租户安全迁移，且支持单看板和整批回滚。
6. 迁移完成后删除旧结构读取逻辑，避免永久双读和长期维护负担。

## 非目标

- 不改版日期入口、日期面板、透视控件或看板卡片布局。
- 不把图表配置全面拆成多张关系表。
- 不根据标题、字段名、第一列、相似字段或历史查询结果猜测业务语义。
- 不自动给没有日期占位符的固定语义指标创建日期筛选。
- 不自动改写任意固定日期 SQL；本次迁移只处理已经使用受控日期占位符或已有完整日期配置的图表。
- 不改变实时图表、外部 MCP 快照和混合数据图表的既有能力边界。

## 方案选择

### 采用方案：独立日期配置

引入版本化 `dateFilter`，保留现有 `pivot` 但收窄其职责。继续使用 `canvas_view_info` 作为图表配置
载体，避免在本次问题范围内进行全面存储重构。

### 未采用：继续复用 `pivot`

该方案改动最小，但无法消除根因。任何根据 `pivot.enabled` 清理、复制或归一化配置的逻辑，仍可能
误删日期参数。

### 未采用：全面结构化图表配置表

该方案治理能力强，但会同时影响图表布局、字段映射、洞察、预测、MCP 和模板等所有看板能力，
不符合本次渐进式改造的成本边界。

## V2 持久化模型

每个 SQL 图表在 `canvas_view_info` 中使用以下结构：

```json
{
  "configVersion": 2,
  "dateFilter": {
    "enabled": true,
    "parameterType": "yyyymmdd_number",
    "expression": {
      "version": 1,
      "mode": "preset",
      "preset": "past_7_days"
    }
  },
  "pivot": {
    "enabled": false
  }
}
```

### `dateFilter`

- `enabled`：是否启用受控 SQL 日期参数。SQL 含受控日期占位符时必须为 `true`。
- `parameterType`：`date`、`yyyymmdd_number`、`yyyymmdd_text` 或 `timestamp`。
- `expression`：版本化默认日期表达式。用户在页面临时选择的日期范围不覆盖持久化表达式。

`parameterMode` 继续由后端根据 SQL 中实际出现的受控 token 推导，不持久化重复状态。

### `pivot`

`pivot` 只保留服务端透视相关配置：

- `enabled`、`client_filter_only`；
- `time_field`、`metric_field`、`metric_fields`；
- `metric_aggregations`、`aggregation`；
- `group_field`、`group_enabled`、`group_values`、`dimensions`；
- `granularity` 及透视自身需要的范围配置。

V2 写入后，`pivot` 中不得再出现 `date_parameter_type` 或 `date_expression`。

### 运行时能力

`dateFilterCapability` 由后端基于当前用户、数据源、SQL 和 V2 配置计算，只存在于接口响应副本，
不得写回 `canvas_view_info`。能力状态保持：

- `available`：配置和模板完整，可以显示日期入口并执行。
- `realtime`：读取实时表，不适用普通历史日期筛选。
- `unconfigured`：配置缺失、待迁移或模板不合法，具体原因放入 `reason`。
- `unsupported`：混合数据、外部 MCP 快照或其他不支持类型。
- `forbidden`：当前权限或执行数据源上下文不允许执行。

## API 请求模型

`/dashboard/sql_preview` 将日期请求和透视请求分开：

```json
{
  "datasource": 6,
  "sql": "SELECT ...",
  "date_filter": {
    "parameter_type": "yyyymmdd_number",
    "expression": {
      "version": 1,
      "mode": "preset",
      "preset": "past_7_days"
    },
    "custom_start": "",
    "custom_end": ""
  },
  "pivot": {
    "enabled": false
  }
}
```

默认加载使用持久化表达式。用户点击日期面板“应用”时，请求传入经过前端格式校验的
`custom_start` 和 `custom_end`；后端仍负责最终自然日、边界和业务时区校验。

SQL 不含受控日期 token 时，`date_filter` 必须为空或禁用。SQL 含受控日期 token 时，缺少有效
`date_filter` 必须返回终态配置错误，不执行 SQL。

## 后端执行顺序

1. 校验用户、租户、工作空间和执行数据源上下文。
2. 解析 V2 日期配置；迁移期内可调用受控 V1 读取器。
3. 扫描 SQL 正文中的受控日期 token，忽略注释、字符串和标识符中的同名文本。
4. 校验 token 家族与 `parameter_type` 完全一致。
5. 解析持久化表达式或用户自定义日期范围。
6. 根据数据源方言渲染日期字面量。
7. 对渲染后的 SQL 执行只读、物理表、字段、行权限和 SQL 安全校验。
8. 执行原始 SQL。
9. 仅在 `pivot.enabled=true` 且非客户端筛选时构造并执行透视聚合。
10. 返回结果、日期能力、刷新时间和结构化错误类型。

缓存键必须包含租户、用户或行权限边界、数据源、SQL 模板、最终日期范围、参数类型和透视配置。
日期配置与透视配置分别规范化后进入缓存键，避免关闭透视改变日期缓存语义。

## 统一写入入口

以下入口必须调用同一套 V2 规范化与验证逻辑：

- SQL 编辑器新建和保存；
- AI 看板 SQL 生成；
- 智能问答图表加入看板；
- 图表复制、看板复制和推荐模板发布；
- 图表类型切换和关闭透视；
- 其他会重建 `canvas_view_info` 图表对象的入口。

统一写入规则：

1. 新写入只允许 `configVersion=2`。
2. SQL 含日期 token 时，必须同时存在完整 `dateFilter`。
3. 关闭透视只修改 `pivot.enabled`，不得清理 `dateFilter`。
4. 固定语义且不含日期 token 的图表不得自动创建 `dateFilter`。
5. 数据源切换后，日期配置必须与 SQL 一起重新验证；不得沿用不匹配的数据源字段或参数类型。
6. 无效配置不得保存到画布。

## 迁移期 V1 读取器

V1 读取器是命名明确的临时兼容模块，只允许两类行为：

1. 旧 `pivot` 同时包含合法 `date_parameter_type`、合法 `date_expression`，且 SQL token 完整匹配时，
   确定性地转换为内存 V2。
2. 任一字段缺失或冲突时，返回 `unconfigured`，原因为 `migration_required`，不补默认值、不执行 SQL。

V1 读取器不得根据标题、SQL 列名或结果字段猜测日期表达式和参数类型。所有保存操作只写 V2。
兼容读取开关关闭后，V1 图表返回明确升级错误；V1 数量归零并稳定一个完整发布周期且不少于
7 个自然日后删除读取器和开关。

## 前端表现约束

正常图表保持现有表现：

- 日期入口位置、样式和日期面板不变；
- 仍然在选择日期后点击“应用”；
- 图表类型、字段映射、透视控件和数据展示不变；
- 不开启透视时仍显示透视关闭，但日期筛选可以独立工作；
- 推荐看板和我的看板保持现有布局。

异常场景调整：

- 配置错误不再长期显示“数据加载中”；
- 无快照时显示明确的图表配置错误；
- 有合法历史快照时保留旧数据并显示刷新失败状态；
- 待迁移但无法自动处理时显示“图表配置待升级”；
- 权限错误不得用旧快照绕过当前权限。

## 图表状态与错误分类

### 图表状态

- `loading`：首次请求执行中。
- `ready`：当前数据有效。
- `refreshing`：保留旧数据并刷新。
- `stale`：刷新失败，但存在当前用户仍有权查看的旧快照。
- `failed`：没有可展示数据，显示明确错误。

请求结束后必须从 `loading` 或 `refreshing` 进入 `ready`、`stale` 或 `failed`。请求版本机制继续阻止旧请求覆盖新请求。

### 终态错误

以下错误不得自动重试：

- `dashboard_date_filter_migration_required`；
- `dashboard_date_filter_unconfigured`；
- `dashboard_date_filter_invalid_template`；
- `permission_denied`；
- `dashboard_execution_datasource_denied`；
- 透视字段或图表配置校验失败；
- SQL 安全和只读校验失败。

### 瞬态错误

只有明确列入白名单的错误允许自动重试：

- `dashboard_query_busy`；
- 请求超时；
- 明确的网络中断；
- 明确标识为可恢复的临时数据源连接错误。

单次刷新最多自动重试 3 次，退避间隔依次为 2 秒、5 秒和 15 秒，并加入不超过 20% 的随机抖动。
重试耗尽后，有快照进入 `stale`，无快照进入 `failed`。
用户手动刷新可以重新执行，但不能绕过配置、权限和 SQL 安全校验。

## 显式存量迁移

### 迁移分类

- `automatic`：V1 日期字段完整，能够机械搬迁到 V2。
- `approved_repair`：配置不完整，但迁移清单明确指定了参数类型和日期表达式。
- `manual_review`：业务语义或参数类型不明确，禁止自动写入。

当前工作空间中已经确认的失败图表属于 `approved_repair`。迁移清单必须按租户、看板和图表 ID
显式记录目标 `parameterType` 与 `expression`，不能通过标题中的“近七天”等文本推断。

### 迁移流程

1. 按租户扫描活动看板的 `canvas_view_info`。
2. 为每张图表输出版本、日期 token、旧配置、迁移分类、目标配置和拒绝原因。
3. 保存完整原始 `canvas_view_info`、内容哈希和迁移批次信息。
4. 预演阶段执行结构校验和日期 SQL 渲染，不写数据库。
5. 人工审核 `approved_repair` 清单；`manual_review` 保持不变。
6. 以单个看板为事务单位写入，并使用租户、看板 ID 和原始 JSON 进行 CAS 更新。
7. 写入后重新读取并验证目标图表；所有非目标图表和非日期配置必须逐字节或结构等价保持不变。
8. 对修复图表执行只读预览，验证日期边界、返回字段和执行耗时。
9. 当前工作空间稳定后，再按租户分批执行相同流程。

迁移工具必须幂等。重复预演或重复执行已经成功迁移的 V2 图表，不得产生新的数据变化。

### 迁移审计

迁移审计需要持久保存：

- 批次号、租户、看板和图表 ID；
- 原始配置恢复快照及原始、新配置哈希；
- 迁移分类、目标日期配置和迁移原因；
- 执行人、执行时间、状态和验证结果；
- CAS 冲突、失败原因和回滚状态。

恢复快照保存在核心系统数据库的迁移审计记录中，不放入业务数据源，也不提交到 Git。

### 回滚

支持按批次或单个看板回滚。回滚同样校验当前 JSON 是否仍等于该迁移生成的新配置：

- 未发生后续编辑时，恢复完整原始 `canvas_view_info`。
- 迁移后用户已经编辑看板时，拒绝自动覆盖，进入人工合并清单。
- 回滚完成后重新读取并校验原始哈希，同时记录回滚审计。

## 代码边界

后端按职责拆分：

- 日期配置模型：V2 数据类型、版本校验和序列化；
- 日期执行器：token 扫描、表达式解析、方言渲染和能力计算；
- V1 读取器：迁移期确定性旧结构转换；
- 配置迁移器：扫描、分类、预演、CAS 写入、验证和回滚；
- 图表执行服务：编排权限、日期渲染、查询、可选透视和缓存。

前端按职责拆分：

- 图表配置规范化模块：所有写入入口生成同一 V2；
- 日期筛选状态模块：保留现有日期交互状态；
- 刷新错误分类模块：终态和瞬态错误白名单；
- 图表加载状态机：统一 `loading`、`ready`、`refreshing`、`stale`、`failed`；
- 异常提示：只处理待迁移、配置错误和刷新失败，不改变正常布局。

不对现有大型 Vue 文件做无关重构；只把本次需要复用和测试的纯配置、错误分类和状态逻辑提取到独立模块。

## 发布顺序

1. 先修复无限加载和错误重试分类，不改变持久化结构。
2. 发布 V2 模型、读取、校验和执行能力，暂时开启完整 V1 配置读取。
3. 所有新增和保存操作开始只写 V2。
4. 预演并迁移当前工作空间，核对页面、结果和性能。
5. 按租户分批迁移；每批独立观察、暂停和回滚。
6. V1 数量归零并稳定一个完整发布周期且不少于 7 个自然日后关闭 V1 读取开关。
7. 关闭开关后再稳定一个完整发布周期且不少于 7 个自然日，删除 V1 读取器、开关和 `pivot`
   旧日期字段。

每一步都必须能独立部署和回滚。状态修复、V2 写入、数据迁移和兼容清理不得捆绑在一次发布中。

## 监控与日志

### 指标

- 各配置版本图表数量及 V1 剩余量；
- 图表加载成功率、失败类型和执行时长；
- 每类错误的自动重试次数和重试耗尽次数；
- `migration_required`、日期模板错误和权限错误数量；
- 迁移成功、跳过、人工审核、CAS 冲突、失败和回滚数量；
- 请求已经结束但仍停留在加载状态的图表数量。

指标标签必须控制基数。租户、看板、图表和 SQL 指纹进入结构化日志，不作为高基数时序指标标签。

### 日志

结构化日志记录租户、用户、看板、图表、数据源、配置版本、错误类型、请求阶段、耗时和 SQL 指纹。
不记录查询结果、凭据、完整敏感参数或用户无权查看的数据。生产常规日志不依赖完整 SQL 文本定位问题。

### 告警和暂停条件

- 终态配置错误发生自动重试时立即告警；
- 迁移出现非目标字段变化时立即停止整批操作；
- 任一写后验证失败、非目标字段变化或 CAS 冲突出现时，立即暂停该租户批次；
- V1 使用量未归零前禁止删除兼容读取器；
- 图表请求结束后仍处于加载状态时记录前端状态异常并上报。

- 迁移后 V1 数量统计准确。

### 集成和浏览器验证

- 当前工作空间失败图表迁移后可以加载，并能切换日期范围；
- 关闭透视时日期控件和实际 SQL 日期范围仍正常；
- 正常图表迁移前后布局、字段和图表结果一致；
- 配置错误显示明确状态，不再长期“数据加载中”；
- 前端请求、后端最终 SQL、缓存日期边界和页面结果相互一致。

## 完成标准

只有同时满足以下条件才可声明完成：

- 正常图表前端表现无变化；
- 日期配置与透视可以独立启停；
- 所有图表请求进入明确终态，不存在永久加载；
- 所有写入入口只产生完整 V2；
- 当前工作空间试点通过结果、权限、日期边界和性能验证；
- 全部存量图表迁移完成或进入明确人工审核清单；
- 迁移具备完整审计、恢复快照和实际回滚验证；
- V1 数量归零并稳定一个完整发布周期且不少于 7 个自然日；
- V1 读取器关闭后无回归，再删除兼容代码和旧字段。
