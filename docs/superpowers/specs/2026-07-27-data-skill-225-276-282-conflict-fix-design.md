# Data Skill 225、276、282 冲突修复设计

## 背景

当前三条 Data Skill 存在交叉约束冲突：

- Skill 282 将“当前”“截至目前”等泛化表达直接判定为未完成当日查询，可能把“当前等级”“截至目前的历史累计”等问题错误强制到 `event_realtime`。
- flam Skill 225 的实时付费定义和部分持久看板 SQL 仍使用 `event`，与 Skill 282 的实时选表校验冲突。
- 修仙 Skill 276 将累计指标定义为 `user.pay.paytotal` 快照，而 Skill 257 要求真实付费金额和付费用户来自 `ServerPayLog.personal.money` 与去重 `uid`。

本次采用已确认的方案 1：统一以交易流水计算所选时间窗口内的累计指标，并收窄平台实时选表触发范围。

## 目标

1. Skill 225 的未完成当日付费查询与 Skill 282 一致使用 `event_realtime`。
2. Skill 276 的累计付费金额和累计付费用户统一由所选窗口内的 `ServerPayLog` 交易流水计算，不使用 `paytotal`。
3. Skill 282 不再因“当前”“截至目前”“截至当前”单独触发实时表。
4. 保持完整历史日查询使用 `event`，避免实时表规则误伤历史分析、快照字段和累计口径。

## 方案对比与结论

### 方案 1：收窄实时词并统一交易流水口径（采用）

- 优点：消除三条 Skill 的直接冲突；金额和人数可在同一窗口、同一事实表上解释；不会把普通“当前”语义误判为实时事件查询。
- 成本：需要同步修改 Skill 文案、SQL 覆盖、校验规则、测试和已发布数据库记录，并刷新 embedding。

### 方案 2：保留 `paytotal` 累计快照并为 Skill 257 增加豁免（不采用）

- 优点：改动较小。
- 缺点：继续保留两套“累计付费”口径，召回顺序变化时仍可能生成不同结果，且豁免会削弱真实交易字段约束。

### 方案 3：只调整 Skill 召回优先级（不采用）

- 优点：无需改业务 SQL。
- 缺点：冲突本身仍存在，显式选择 Skill、召回预算或向量排序变化后会再次暴露。

## 详细设计

### Skill 282：平台实时选表

实时触发词只保留以下七项：

- `今天`
- `当天`
- `今日`
- `实时`
- `当前小时`
- `当前分钟`
- `当前整点`

从实时触发集合明确删除：

- `当前`
- `截至目前`
- `截至当前`

删除仅针对 Skill 282 的实时选表匹配和说明文本，不要求从其他业务 Skill 中全局删除这些自然语言。它们可以继续描述累计快照或回答时点，但不能单独成为 `event_realtime` 的选表依据。

选表规则如下：

- 问题命中保留触发词，并且 SQL 涉及 `event`/`event_realtime` 事件表时，未完成当天部分必须使用 `event_realtime`。
- “当前等级”“当前快照”“截至目前的历史累计”“截至当前的完整历史日”等表达若未命中保留触发词，不强制使用 `event_realtime`。
- 昨天、截至昨天、明确结束日期、完整自然日和不含今天的历史趋势使用 `event`。
- 跨日窗口明确包含今天时，历史完整日使用 `event`，今天使用 `event_realtime`；只有 Schema 和业务语义允许时才合并。
- 缺少实时表、权限或元数据时明确报错，不静默回退到 `event`。

### Skill 225：flam 实时付费

- “今天/当天/今日/实时/当前小时/当前分钟/当前整点”的付费金额、付费人数、支付次数和小时趋势均查询 `event_realtime`。
- 交易事件固定为 `ServerPayLog`，金额读取 `personal.money`，付费用户按 `uid` 去重；支付次数沿用组件既有定义。
- 同步修改冲突组件 `4fc570b4be7d406c9f648d9088f760bb` 与 `2149b7abbc6c4cd7ad6f52379e69b15a` 的 SQL 源及覆盖清单，确保 SQL 不再引用历史表 `event`。
- 完整历史日付费仍使用 `event`，不因这次修复全部切换到实时表。
- flam 业务时区继续使用 UTC+8；实时 SQL 的业务日期和小时边界按既有时区规则计算。

### Skill 276：修仙窗口累计付费

“累计”统一解释为用户选择时间窗口内的累计，而不是用户生命周期累计快照：

- 窗口累计付费金额：对窗口内 `event = 'ServerPayLog'` 的 `personal.money` 求和。
- 窗口累计付费用户：对窗口内出现过 `ServerPayLog` 的 `uid` 做 `COUNT(DISTINCT uid)`。
- 按日累计趋势：先计算每日交易金额和每日首次出现的付费用户，再使用窗口函数得到截至当日累计金额与累计去重付费用户，不能把每日去重人数直接相加。
- 禁止使用 `user.pay.paytotal` 生成上述金额、人数或趋势。
- 等级分层等明确要求“用户生命周期累计快照”的独立问题不由 Skill 276 的窗口累计规则兜底；如仍需支持，必须由不与 Skill 257 冲突的独立、明确 Skill 描述。

### 配置与发布

代码库中的种子脚本和 SQL 覆盖文件是配置源，数据库中的 Data Skill 记录是运行时实际配置。实施时需：

1. 更新 Skill 282 平台种子、Skill 225 flam 种子及 SQL 覆盖、Skill 276 修仙种子和目录描述。
2. 使用现有幂等发布脚本更新对应租户、工作空间和数据源范围内的记录，不创建重复 Skill。
3. 对更新记录执行版本或内容校验，避免覆盖并发修改。
4. 刷新变更 Skill 的 embedding，确保召回文本与数据库正文一致。
5. 回读 Skill ID、作用域、正文、校验声明和 embedding 状态，不能只以脚本退出码作为发布成功证据。

## 测试设计

### 静态与单元测试

- Skill 282 的匹配集合精确等于七个保留触发词。
- `当前`、`截至目前`、`截至当前` 均不是 Skill 282 匹配数组中的独立元素，规则说明也不能把它们描述为可单独触发实时选表。
- flam Skill 225 的两个目标 SQL 只使用 `event_realtime`，包含 `ServerPayLog` 和正确金额/用户字段。
- 修仙 Skill 276 的累计 SQL 包含 `ServerPayLog`、`$.money`、`COUNT(DISTINCT uid)`，且不包含 `paytotal`。
- SQL 校验器对冲突前 SQL 返回违规，对修复后 SQL 通过。

### 语义回归场景

- “今天按小时统计付费金额”使用 `event_realtime`。
- “当前小时付费用户数”使用 `event_realtime`。
- “当前等级分布”不因“当前”被强制到 `event_realtime`。
- “截至目前的历史累计付费趋势”不因“截至目前”被强制到 `event_realtime`，具体窗口由问题日期或澄清结果决定。
- “截至当前的完整历史日付费”不因“截至当前”被强制到 `event_realtime`。
- “最近 15 天累计付费金额”从 `ServerPayLog.personal.money` 计算。
- “最近 15 天累计付费用户数”按全窗口 `uid` 去重，不能累计每日去重人数。

### 发布后验证

- 数据库回读 225、276、282 的最新正文和作用域。
- 分别显式选择和自动召回相关 Skill，确认组合后的校验规则无冲突。
- 检查生成 SQL 的物理表、金额字段、去重方式和日期边界。
- 在目标数据源执行有界查询，核对结果可执行且符合窗口累计语义。

## 非目标

- 不修改通用后端代码以硬编码 flam、修仙、付费或表名规则。
- 不把所有包含“当前”的业务问题改为历史查询；是否实时由收窄后的明确触发词和日期语义共同决定。
- 不全仓库删除“截至目前”“截至当前”文字；只从实时选表触发条件和相应说明中移除。
- 不在本设计阶段发布数据库、修改生产配置、提交或推送实现代码。

## 验收标准

- Skill 225、276、282 同时召回时不再产生表选择或付费字段校验冲突。
- 七个保留实时词可稳定触发未完成当日 `event_realtime` 规则。
- “当前”“截至目前”“截至当前”单独出现时不会触发该规则。
- 225 的实时付费 SQL 与 282 一致；276 的累计指标与 257 一致。
- 定向测试、数据库回读、embedding 刷新和实际召回验证均有可复核证据。
