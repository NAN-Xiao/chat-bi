# Data Skill 225、257、276、280、282 与 234 冲突修复设计

## 背景

当前三条 Data Skill 存在交叉约束冲突：

- Skill 282 将“当前”“截至目前”等泛化表达直接判定为未完成当日查询，可能把“当前等级”“截至目前的历史累计”等问题错误强制到 `event_realtime`。
- flam Skill 225 的实时付费定义和部分持久看板 SQL 仍使用 `event`，与 Skill 282 的实时选表校验冲突。
- 修仙 Skill 276 将累计指标定义为 `user.pay.paytotal` 快照，而 Skill 257 要求真实付费金额和付费用户来自 `ServerPayLog.personal.money` 与去重 `uid`。
- 用户私有 Skill 280 明确描述修仙 `ResourceChange`，但当前 `specific_ds=false`，可能泄漏到该用户可访问的其他数据源。
- 平台 Skill 234 只有“不要全表扫描，先用时间过滤”的宽泛规则，与平台 Skill 171 的时间边界规则重复，且没有说明适用表、已确认时间字段和无时间条件时的处理方式。

本次采用已确认的方案 1：统一以交易流水计算所选时间窗口内的累计指标，并收窄平台实时选表触发范围。

## 目标

1. Skill 225 的未完成当日付费查询与 Skill 282 一致使用 `event_realtime`。
2. Skill 276 的累计付费金额和累计付费用户统一由所选窗口内的 `ServerPayLog` 交易流水计算，不使用 `paytotal`。
3. Skill 282 不再因“当前”“截至目前”“截至当前”单独触发实时表。
4. 保持完整历史日查询使用 `event`，避免实时表规则误伤历史分析、快照字段和累计口径。
5. Skill 280 仅在修仙数据源 6 中可召回，保留原用户私有属性和所有权。
6. 将 Skill 234 的有效意图收敛进 Skill 171 后停用 234，消除重复、无条件的平台规则。
7. 固化四个已复现问题的召回组合与 SQL 校验回归，防止修复依赖召回顺序。

## 方案对比与结论

### 方案 1：收窄实时词并统一交易流水口径（采用）

- 优点：消除三条 Skill 的直接冲突；金额和人数可在同一窗口、同一事实表上解释；不会把普通“当前”语义误判为实时事件查询。
- 成本：需要同步修改 Skill 文案、SQL 覆盖、校验规则、测试和已发布数据库记录，并刷新 embedding。

### 方案 2：保留 `paytotal` 累计快照并为 Skill 257 增加豁免（不采用）

- 优点：改动较小。
- 缺点：继续保留两套“累计付费”口径，召回顺序变化时仍可能生成不同结果，且豁免会削弱真实交易字段约束。

### 方案 3：只调整 Skill 召回优先级（不采用）

- 优点：无需改业务 SQL。
- 缺点：冲突本身仍存在，显式选择 Skill、召回预算或向量排序变化后会再次暴露。

## 详细设计

### Skill 282：平台实时选表

实时触发词只保留以下七项：

- `今天`
- `当天`
- `今日`
- `实时`
- `当前小时`
- `当前分钟`
- `当前整点`

从实时触发集合明确删除：

- `当前`
- `截至目前`
- `截至当前`

删除仅针对 Skill 282 的实时选表匹配和说明文本，不要求从其他业务 Skill 中全局删除这些自然语言。它们可以继续描述累计快照或回答时点，但不能单独成为 `event_realtime` 的选表依据。

选表规则如下：

- 问题命中保留触发词，并且 SQL 涉及 `event`/`event_realtime` 事件表时，未完成当天部分必须使用 `event_realtime`。
- “当前等级”“当前快照”“截至目前的历史累计”“截至当前的完整历史日”等表达若未命中保留触发词，不强制使用 `event_realtime`。
- 昨天、截至昨天、明确结束日期、完整自然日和不含今天的历史趋势使用 `event`。
- 跨日窗口明确包含今天时，历史完整日使用 `event`，今天使用 `event_realtime`；只有 Schema 和业务语义允许时才合并。
- 缺少实时表、权限或元数据时明确报错，不静默回退到 `event`。

### Skill 225：flam 实时付费

- “今天/当天/今日/实时/当前小时/当前分钟/当前整点”的付费金额、付费人数、支付次数和小时趋势均查询 `event_realtime`。
- 交易事件固定为 `ServerPayLog`，金额读取 `personal.money`，付费用户按 `uid` 去重；支付次数沿用组件既有定义。
- 同步修改冲突组件 `4fc570b4be7d406c9f648d9088f760bb` 与 `2149b7abbc6c4cd7ad6f52379e69b15a` 的 SQL 源及覆盖清单，确保 SQL 不再引用历史表 `event`。
- 完整历史日付费仍使用 `event`，不因这次修复全部切换到实时表。
- flam 业务时区继续使用 UTC+8；实时 SQL 的业务日期和小时边界按既有时区规则计算。

### Skill 276：修仙窗口累计付费

“累计”统一解释为用户选择时间窗口内的累计，而不是用户生命周期累计快照：

- 窗口累计付费金额：对窗口内 `event = 'ServerPayLog'` 的 `personal.money` 求和。
- 窗口累计付费用户：对窗口内出现过 `ServerPayLog` 的 `uid` 做 `COUNT(DISTINCT uid)`。
- 按日累计趋势：先计算每日交易金额和每日首次出现的付费用户，再使用窗口函数得到截至当日累计金额与累计去重付费用户，不能把每日去重人数直接相加。
- 禁止使用 `user.pay.paytotal` 生成上述金额、人数或趋势。
- 等级分层等明确要求“用户生命周期累计快照”的独立问题不由 Skill 276 的窗口累计规则兜底；如仍需支持，必须由不与 Skill 257 冲突的独立、明确 Skill 描述。

### Skill 257：修仙交易校验拆分

Skill 257 保持 `ServerPayLog` 为真实交易事实来源，但按问题类型拆分结构化校验，避免“付费用户数”被无关金额字段阻塞：

- 付费金额、收入、流水、ARPU、ARPPU：要求 `ServerPayLog` 和 `personal.money`，禁止 `PayBuyRet`、`ed_money` 与 `paytotal`。
- 付费用户数、付费人数：要求 `ServerPayLog` 和 `COUNT(DISTINCT uid)`，不要求 SQL 出现 `personal.money`。
- 累计付费金额：与 Skill 276 一致，要求窗口内 `ServerPayLog.personal.money` 求和。
- 累计付费用户数：与 Skill 276 一致，要求窗口内 `ServerPayLog.uid` 全窗口去重，不要求无关金额表达式。
- 同一个问题同时请求金额和人数时，两组要求同时生效。

### Skill 280：修仙资源口径的数据源隔离

- 保留 Skill 280 的 `USER_PRIVATE`、原 `tenant_id`、`create_by`、正文和用户启用偏好。
- 将 `specific_ds` 从 `false` 改为 `true`，将 `datasource_ids` 精确设置为 `[6]`。
- 更新后清空旧 embedding 与签名并重新生成，避免使用旧的无数据源范围向量状态。
- 在数据源 6 中，资源获取、消耗、净变化和 `ResourceChange` 问题仍可召回 280。
- 在 flam 数据源 3、SLG 数据源 1 或其他数据源中，同一用户也不能召回 280。

### Skill 171 与 234：合并后停用重复规则

- 将 Skill 234 的有效意图合并到平台 Skill 171：对高成本事实明细查询，只有在当前 Schema 或工作空间元数据已确认业务时间字段时，才应先施加用户指定或平台允许的有界时间/分区条件，再执行明细扫描。
- 不把“所有查询都必须有时间过滤”设为无条件规则；维表、小表、无时间字段表和明确的非时间分析不应被错误阻断。
- Skill 171 的现有日期锚点、空间 Skill 优先级和权限边界保持不变。
- 合并并刷新 Skill 171 embedding 后，将 Skill 234 设置为 `active=false, visible=false`，同时清空其 embedding 与签名；不物理删除记录，保留审计与回滚能力。
- 自动召回、显式可选列表和运行时拼接均不得再返回 Skill 234。

### 配置与发布

代码库中的种子脚本和 SQL 覆盖文件是配置源，数据库中的 Data Skill 记录是运行时实际配置。实施时需：

1. 更新 Skill 282 平台种子、Skill 225 flam 种子及 SQL 覆盖、Skill 257/276 修仙种子和目录描述。
2. 增加可重复执行的治理脚本，以当前 ID、名称、作用域和内容摘要作并发保护，更新 171、234、280；任何前置状态不匹配时拒绝部分写入。
3. 对更新记录执行版本或内容校验，避免覆盖并发修改。
4. 刷新变更 Skill 的 embedding，确保召回文本与数据库正文一致。
5. 回读 Skill ID、作用域、正文、校验声明、活动状态和 embedding 状态，不能只以脚本退出码作为发布成功证据。

## 测试设计

### 静态与单元测试

- Skill 282 的匹配集合精确等于七个保留触发词。
- `当前`、`截至目前`、`截至当前` 均不是 Skill 282 匹配数组中的独立元素，规则说明也不能把它们描述为可单独触发实时选表。
- flam Skill 225 的两个目标 SQL 只使用 `event_realtime`，包含 `ServerPayLog` 和正确金额/用户字段。
- 修仙 Skill 276 的累计金额 SQL 包含 `ServerPayLog` 和 `$.money`；累计用户 SQL 包含 `ServerPayLog` 和 `COUNT(DISTINCT uid)`；两者均不包含 `paytotal`。
- Skill 257 的付费金额规则要求 `$.money`；仅付费用户数规则不要求 `$.money`，但要求 `COUNT(DISTINCT uid)`。
- Skill 280 的治理更新只改变数据源范围和 embedding 状态，不改变所有权、可见性或正文。
- Skill 234 停用后不可召回，Skill 171 包含带适用条件的有界扫描规则。
- SQL 校验器对冲突前 SQL 返回违规，对修复后 SQL 通过。

### 四个固定召回与校验回归

| 数据源 | 问题 | 完整上下文应包含 | 实际生效的业务校验 | 修复后 SQL 要点 |
| --- | --- | --- | --- | --- |
| flam 3 | `今天实时付费趋势` | 225、282；不含 234、280 | 225 的交易规则、282 的实时选表规则 | `event_realtime`、`ServerPayLog`，不引用历史表 `event` |
| 修仙 6 | `按渠道统计累计付费用户数` | 257、276、282；不含 234 | 257/276 的窗口累计用户规则；282 实时规则不命中 | 窗口内 `ServerPayLog`，按渠道对 `uid` 全窗口去重，不使用 `paytotal` |
| 修仙 6 | `统计昨天的付费用户数` | 257、282；不含 234 | 257 的付费用户规则；282 实时规则不命中 | 历史表 `event`、`ServerPayLog`、`COUNT(DISTINCT uid)`，不强制 `$.money` |
| 修仙 6 | `当前等级的活跃用户分布` | 255、278、282；不含 234 | 255/278 的完整日活跃快照规则；282 实时规则不命中 | 昨天完整日 `event` 的 `UserActive` 关联同日 `user` 快照，不使用 `event_realtime` |

测试必须覆盖实际 `find_data_skills` 得到的自动上下文组合、显式组合后的完整 Skill 文本，以及 `_data_skill_sql_validation_violation` 的真实校验结果。基础 Skill 被注入上下文但其规则未命中，应与 Skill 完全未召回分别断言；不能只断言某个 Skill 文本包含关键词。

### 数据源隔离回归

- 使用 Skill 280 的所有者身份，在数据源 6 询问“近 7 天钻石获取、消耗和净变化趋势”，应召回 280。
- 同一身份在数据源 3 或 1 提问相同问题，不得召回 280，也不得把 `ResourceChange` 或修仙资源编码注入上下文。
- 平台 Skill 234 在任意数据源、自动模式和显式可选列表中均不可用。

### 语义回归场景

- “今天按小时统计付费金额”使用 `event_realtime`。
- “当前小时付费用户数”使用 `event_realtime`。
- “当前等级分布”不因“当前”被强制到 `event_realtime`。
- “截至目前的历史累计付费趋势”不因“截至目前”被强制到 `event_realtime`，具体窗口由问题日期或澄清结果决定。
- “截至当前的完整历史日付费”不因“截至当前”被强制到 `event_realtime`。
- “最近 15 天累计付费金额”从 `ServerPayLog.personal.money` 计算。
- “最近 15 天累计付费用户数”按全窗口 `uid` 去重，不能累计每日去重人数。

### 发布后验证

- 数据库回读 225、276、282 的最新正文和作用域。
- 数据库回读 171、234、257、280 的正文、活动状态、所有权与数据源范围。
- 分别显式选择和自动召回相关 Skill，确认组合后的校验规则无冲突。
- 检查生成 SQL 的物理表、金额字段、去重方式和日期边界。
- 在目标数据源执行有界查询，核对结果可执行且符合窗口累计语义。

## 非目标

- 不修改通用后端代码以硬编码 flam、修仙、付费或表名规则。
- 不把所有包含“当前”的业务问题改为历史查询；是否实时由收窄后的明确触发词和日期语义共同决定。
- 不全仓库删除“截至目前”“截至当前”文字；只从实时选表触发条件和相应说明中移除。
- 不把 Skill 280 改为工作空间公共 Skill，也不转移其所有者。
- 不物理删除 Skill 234；本次采用可回滚的停用方式。
- 不在本设计阶段发布数据库、修改生产配置、提交或推送实现代码。

## 验收标准

- Skill 225、276、282 同时召回时不再产生表选择或付费字段校验冲突。
- 七个保留实时词可稳定触发未完成当日 `event_realtime` 规则。
- “当前”“截至目前”“截至当前”单独出现时不会触发该规则。
- 225 的实时付费 SQL 与 282 一致；276 的累计指标与 257 一致。
- 280 只在数据源 6 召回；234 不再出现在任何活动 Skill 组合中，其有效约束由 171 有条件承接。
- 四个固定问题的自动召回组合和真实 SQL 校验均通过，且不依赖 18,000 字符预算或向量排序偶然性。
- 定向测试、数据库回读、embedding 刷新和实际召回验证均有可复核证据。
