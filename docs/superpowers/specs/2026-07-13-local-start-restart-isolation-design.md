# 本地启动与任务队列隔离设计

## 背景

用户在当前工作区说“启动”或“重启”时，意图是操作 `D:\AIWork3\chat-bi` 本地开发环境。现有本地启动技能只启动前端、API 和 MCP，没有启动本地任务 Worker；同时本地 API 与生产 Worker 都连接 `10.1.5.28:6379/0`，并使用 `REDIS_KEY_PREFIX=shuzhi`、`TASK_QUEUE_NAME=default`。因此，本地 Smart Q&A 任务可能被生产 Worker 消费，实际执行代码和超时配置与本地进程不一致。

仓库现有 `tools/stack-local.ps1`、`tools/backend-local.ps1` 和 `tools/worker-local.ps1` 已支持按“计算机名 + 工作区名”生成本地独立队列，并把同一个队列名传给本地 API 和 Worker。本设计复用该能力，不新建任务队列实现。

## 目标

- 无修饰的“启动”“重启”“本地启动”“本地重启”只操作当前 Windows 本地工作区。
- 默认启动前端 `5173`、后端 API `8000`、MCP `8001` 和一个本地任务 Worker。
- 本地 API 与本地 Worker 使用同一个独立队列 `local-<计算机名>-chat-bi`。
- 本地 Smart Q&A 任务不得进入生产使用的 `default` 队列。
- 本地模型读取超时使用当前代码配置 `LLM_REQUEST_TIMEOUT=120`。
- 除非用户明确说明“生产”“远程”“Jenkins”或具体服务器，否则启动和重启不得执行 SSH、Docker、Jenkins或生产容器操作。

## 非目标

- 不修改生产队列名、生产 Redis 前缀或生产容器编排。
- 不为本地环境新建 Redis 实例或切换 Redis DB。
- 不改变 Smart Q&A 任务数据结构、任务状态机或 Worker 消费算法。
- 不改变大模型超时值、重试次数或任务总等待上限。
- 不默认启动本地 Nginx 或多后端副本。

## 方案

### 命令语义

更新仓库 `AGENTS.md` 与 `starting-chat-bi-local` 技能，建立以下默认解释：

| 用户表达 | 默认操作 |
| --- | --- |
| 启动、开始、本地启动 | 启动当前工作区的完整本地开发栈 |
| 重启、重新启动、本地重启 | 重启当前工作区的完整本地开发栈 |
| 查看状态、启动状态 | 查看当前工作区本地服务状态 |
| 生产启动、生产重启、重启服务器 | 必须按用户明确指定的生产范围另行处理 |

无修饰的启动类表达不得推断为生产操作。

### 本地服务组成

完整本地开发栈包含：

1. 前端 Vite：`0.0.0.0:5173`。
2. 后端 API：`0.0.0.0:8000`。
3. MCP 应用：`0.0.0.0:8001`，保持 `MCP_ENABLED=false`，除非用户明确测试 MCP 访问控制。
4. 本地任务 Worker：默认一个进程。

数据库和 Redis 继续使用仓库规定的核心端点。Nginx、额外后端副本和额外 Worker 不属于无修饰“启动”的默认范围。

### 队列隔离

本地队列名沿用现有脚本算法：

```text
local-<COMPUTERNAME>-<workspace-folder>
```

在当前工作区中，工作区目录名为 `chat-bi`。脚本需要将非字母、数字、点、下划线和连字符替换为连字符。

同一次启动中：

- 后端 API 的 `TASK_QUEUE_NAME` 必须等于该本地队列名。
- MCP 进程使用相同的本地环境配置。
- 本地 Worker 必须监听相同队列名。
- 不得回退到 `default` 队列。

复用 `tools/stack-local.ps1` 负责 API、MCP、Worker 和队列名传递；前端仍按现有 Vite 启动方式单独管理。这样保留现有脚本职责，避免扩展 `stack-local.ps1` 去管理 Node.js 前端。

## 启动流程

### 启动

1. 检查 `5173`、`8000`、`8001` 和本地 Worker 状态。
2. 计算当前工作区的本地队列名。
3. 使用 `tools/stack-local.ps1 -Action start -StartMcp -SkipNginx` 启动 API、MCP 和一个本地 Worker。
4. 若前端未运行，使用现有 `npm run dev` 命令启动前端并写入 `.codex-runtime` 日志。
5. 验证端口、HTTP 响应、Worker PID 和队列名。

若某个本地服务已经健康，则保留该服务，不启动重复进程；但必须确认现有 API 和 Worker 的队列一致。无法确认时应执行一次本地重启，使环境变量重新加载。

### 重启

1. 只停止当前工作区拥有的前端、API、MCP 和本地 Worker 进程。
2. 不停止远程 PostgreSQL、远程 Redis、生产容器、Jenkins 或其他工作区进程。
3. 使用与“启动”相同的队列名重新启动完整本地开发栈。
4. 执行完整验证。

现有不带 PID 文件、但占用本地目标端口的旧启动进程，可以在重启时按端口停止；仅允许目标端口 `5173`、`8000` 和 `8001`。

## 验证标准

启动或重启完成后必须同时满足：

- `http://127.0.0.1:5173/` 返回 `200`。
- `http://127.0.0.1:8000/api/v1/system/getLoginMethod` 返回 HTTP 响应；`401` 也表示 API 已启动。
- `8001` 正在监听；根路径返回 `404` 也表示 MCP 应用已启动。
- 本地 Worker PID 文件存在，进程仍在运行。
- Worker 日志包含本地独立队列名，不是 `default`。
- 新启动的本地配置解析结果为：

```text
LLM_REQUEST_TIMEOUT=120
LLM_TASK_MAX_WAIT_SECONDS=900
LLM_MAX_RETRIES=1
```

- API 与 Worker 的 `TASK_QUEUE_NAME` 完全一致。

## 错误处理

- 核心数据库或 Redis 不可达时，启动失败并报告实际端点，不尝试旧本地数据库或随机端口。
- 本地 Worker 启动失败时，不得把 Smart Q&A 可用性标记为正常；应指出队列任务将无法在本地执行。
- 端口被非当前工作区进程占用时，启动操作报告占用者；只有“重启”可停止目标端口拥有者。
- 队列名不一致时，停止相关本地进程并使用同一队列名重新启动，不允许回退到生产 `default` 队列。

## 修改范围

- 修改仓库 `AGENTS.md`：明确无修饰“启动/重启”的本地语义、默认四服务和独立队列要求。
- 修改 `starting-chat-bi-local` 技能：复用 `tools/stack-local.ps1` 管理 API、MCP 和 Worker，并保留前端启动与验证步骤。
- 不修改任务队列 Python 实现。
- 不修改生产环境文件。

## 测试

- 静态验证启动规范包含本地限定、四服务、独立队列和生产操作禁令。
- 对 PowerShell 启动命令执行语法检查。
- 执行一次本地重启，验证 `5173`、`8000`、`8001`、Worker PID 和 Worker 队列日志。
- 从本地进程读取模型超时配置，确认 `120/900/1`。
- 检查生产 Worker 日志在验证时间窗内没有消费本地独立队列任务。

## 风险与回滚

本地启动将比旧三服务流程多启动一个 Worker，增加少量本机资源占用。独立队列上的任务只有本地 Worker 能处理，因此 Worker 停止时任务会保持待处理，而不会再由生产 Worker 兜底；这是环境隔离所需的显式失败方式。

回滚时可恢复旧启动技能和 `AGENTS.md` 说明，但不建议恢复 `default` 队列共享行为。若临时不测试队列任务，应显式使用 `-SkipWorker`，而不是让生产 Worker 处理本地任务。
