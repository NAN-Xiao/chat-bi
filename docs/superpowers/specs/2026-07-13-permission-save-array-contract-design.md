# 字段权限保存数组契约修复设计

## 背景

字段权限页面最终保存规则组时，会把每条字段权限的 `permissions` 数组提前执行
`JSON.stringify`。后端新增 JSON 子字段身份校验后，接口要求该字段保持数组，因此保存请求在进入字段逐项校验前返回“字段权限配置必须是列表”。

## 目标

- 当前前端提交字段权限时使用数组，不再提交 JSON 字符串。
- 后端继续严格要求数组，不增加旧字符串格式的静默兼容。
- 不修改 SQL 权限判定、历史结果重检、行权限注入和数据库存储格式。
- 禁用 `event.personal.money` 后，普通用户的 ARPU 查询和历史结果必须被当前权限拦截。

## 方案

将权限保存载荷转换提取为前端纯函数，并由权限页面统一调用：

- `column` 权限的 `permissions` 保持字段条目数组。
- `row` 权限的 `permissions` 固定为空数组，`expression_tree` 保持对象。
- `table` 权限的 `permissions` 固定为空数组，`expression_tree` 固定为空对象。
- 后端 `normalize_permission_field_entries` 继续校验数组内每个物理字段或 JSON 子字段的身份与归属。
- 持久化层继续通过 `_json_text` 将数组或对象序列化为数据库文本字段。

不采用后端同时接受字符串和数组的兼容方案，因为这会掩盖客户端请求契约错误，并违反仓库“不增加静默兼容回退”的约束。

## 数据流

1. 权限编辑表单维护字段条目数组。
2. 前端载荷转换函数按权限类型生成结构化请求。
3. 后端验证数据源、数据表和字段身份。
4. 持久化层统一序列化后写入 `ds_permission`。
5. 查询时沿用现有权限读取、SQL 范围校验和历史数据重检流程。

## 错误处理

- 非数组字段权限继续返回 HTTP 400。
- 伪造或不属于当前工作空间的 JSON 子字段继续返回 HTTP 400。
- 前端不捕获并改写这些后端校验结果，沿用现有错误提示机制。

## 测试与验收

- 先增加前端失败测试，证明旧转换会把字段数组变成字符串。
- 验证 `column`、`row`、`table` 三类载荷的数据类型。
- 运行现有 JSON 子字段前端检查和后端权限专项测试。
- 构建前端，确保类型检查通过。
- 本地保存规则组，确认不再出现“字段权限配置必须是列表”。
- 将 `event.personal.money` 设为不可见后，用普通账号验证 ARPU 新查询和 `record_id=495` 历史数据均不能继续返回金额结果。

## 非目标

- 不兼容继续发送字符串字段权限的旧客户端。
- 不修改工作空间成员默认的数据源访问模型。
- 不根据字段名称自动推断“金额相关字段”。
- 不变更现有权限数据，除非管理员在界面中明确保存新的字段选择。
