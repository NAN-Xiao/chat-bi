# flam 与修仙 AI 看板 200 题测试设计

## 背景

本次测试基于当前系统数据库中的推荐看板，分别为 `flam` 空间和`修仙`空间生成 100 个问题，并通过本地 AI 看板真实 UI 完成提交、等待和结果采集。

`flam` 空间明确排除推荐入口“运营总览”及其内容。其余推荐入口均需检查；无法打开有效看板内容的入口记录为导航或配置问题，不生成无依据问题，也不通过重复提交凑数。`修仙`空间覆盖全部当前推荐看板。

## 目标

- 为两个空间分别生成 100 个唯一、可审计的问题。
- 问题覆盖当前推荐看板的指标、维度、趋势、对比和业务解读能力。
- 通过真实 UI 验证空间上下文、问题提交、SQL/数据返回、图表生成及多轮追问链路。
- 区分运行完成、完整 SQL、图表展示、能力边界和产品错误。
- 产出可逐题追溯的题目、结果和汇总报告。

## 非目标

- 不修改推荐看板、Data Skill、数据源、权限或业务数据。
- 不把接口直调结果替代真实 UI 测试结果。
- 不把抽屉中有限的历史记录作为批量审计依据。
- 不因看板缺少内容而从其他看板静默借用指标。
- 不要求所有问题都使用最近 28 天，也不要求每题新建会话。

## 方案选择

### 方案一：真实 UI 全链路测试

采用。能够同时验证推荐看板入口、空间上下文、抽屉交互、AI 任务、SQL/数据和图表结果，符合本次测试目的。

### 方案二：后端接口批量提交

执行速度较快，但不能覆盖推荐看板导航、抽屉状态和浏览器图表渲染，不采用。

### 方案三：只生成问题清单

不能证明 AI 看板实际完成提问与返回，不采用。

## 推荐看板范围

测试开始前从当前系统数据库和 UI 各盘点一次推荐看板，并保存看板 ID、名称、数据源、入口状态和图表标题摘要。

- `flam`：排除名称为“运营总览”的入口及其内容；其余入口逐一检查。
- `修仙`：全部推荐入口逐一检查。
- 普通数据看板和外部 MCP 看板分别标记，避免混淆 SQL 数据能力与外部工具能力。
- 文件夹、空看板、错误落页或数据源不匹配均形成独立缺陷记录。
- 问题只从可见看板内容、图表配置和当前空间语义配置生成。

## 问题设计

每个空间生成 20 个主题会话，每个会话连续提出 5 个问题，共 100 个问题。后续问题可以引用同一会话的上一题结果，用于验证多轮上下文。

问题类型混合分布：

- 单指标查询与核心指标组合。
- 按渠道、服务器、地区或看板现有维度拆分。
- 日、周、月趋势以及环比、占比和排名。
- 留存、付费、活跃、增长、活动、经济或投放等看板实际配置主题。
- 异常识别、重点总结和基于已有结果的追问。
- 外部 MCP 看板对应的问题仅使用其已配置的工具能力。

时间范围混合昨天、近 3/7/14/21/30/60/90 天、本周、本月、指定区间和不限定时间的问题。涉及当前业务数据诊断但未指定时间的问题，遵循平台现有的最近 28 天及最大业务日期锚点规则。

两套题目必须各自满足：ID 唯一、问题文本唯一、会话号完整、空间归属明确，并不得复用另一个空间的专有指标或字段。

## 执行流程

1. 验证本地前端 `5173`、API `8000`、MCP `8001` 和独立队列 Worker，核对模型超时配置为 `120 900 1`。
2. 在 UI 中分别进入两个空间，核对当前空间、绑定数据源和推荐看板入口。
3. 先完成一个空间的全部测试和结果采集，再切换另一个空间，避免跨空间请求残留。
4. 使用最多 4 个浏览器执行通道，与本地 Worker 并发能力保持一致；同一会话内的 5 个问题严格串行。
5. 每题记录空间、看板、数据源、问题 ID、会话号、问题文本、请求或记录 ID、开始时间、结束时间和最终状态。
6. 初次失败的问题在健康检查后使用独立会话复测一次；依赖上下文的问题重放完整五题会话后再判定。
7. 不覆盖初次结果，复测作为独立尝试保存，并在最终报告中说明采用哪次结果及原因。

## 验收规则

题库中的每一道题按“完整 SQL + 图表展示”验收。只有同一次提问尝试同时满足以下条件，`status` 才能标记为 `success`：

1. AI 看板在一次完整流程中生成了可执行的完整 SQL，结果记录的 `has_sql_answer=true`，SQL 非空且不是截断内容。
2. SQL 执行流程正常结束，未出现 SQL 生成、校验、执行或任务错误。
3. 当前 AI 看板页面实际展示了图表，结果记录的 `has_chart_answer=true`，且浏览器存在当前题目对应的可见图表组件；仅收到文本回答、SQL、数据表或图表配置 JSON，均不能证明图表已展示。
4. SQL 和图表必须属于同一个 `question_id`、`attempt_id` 和 `record_id`。不能把一次尝试的 SQL 与另一次重试的图表合并为成功。

首次提交未同时满足以上条件即为失败。人工点击重新生成或独立会话复测只能新增一条 attempt，不能把首次结果改写为成功；复测成功也必须在报告中保留首次失败原因。

特别地，`has_sql_answer=true` 但没有图表的题必须进入“未生成图表问题”清单，即使有数据、有文本回答、任务状态为完成或 SQL 执行成功，也不得计入成功数。

每题结果至少记录以下字段：`question_id`、`attempt_id`、`record_id`、`finish`、`has_complete_sql`、`has_sql_answer`、`has_chart_answer`、`chart_rendered`、`status`、`chart_not_generated`、`chart_not_generated_reason`、`screenshot_path`。其中 `chart_rendered` 必须来自当前题目页面的 DOM/截图证据，不得仅依据数据库中的 `chart` 字段推断。

## 结果分类

每题必须且只能归入一个最终类别：

- `success`：一次完整生成 SQL，SQL 执行完成，并在当前 AI 看板页面展示图表。
- `chart_not_generated`：已生成完整 SQL 或返回数据/文本，但没有生成图表、图表配置无效或页面没有展示图表；必须写入未生成图表问题清单。
- `sql_not_generated`：没有得到一次完整可执行 SQL。
- `sql_error`：SQL 生成、校验或执行失败。
- `chart_error`：已进入图表阶段，但图表配置解析或前端渲染失败。
- `capability_boundary`：明确说明当前数据、语义或外部工具能力边界；不计入成功。
- `runtime_error`：网络、Worker、任务状态或其他运行链路失败。
- `running_or_orphaned`：超过等待窗口仍未结束，必须复测并单独报告。

`data_text_success`、`text_success` 和“请求已完成”不再是成功类别。最终汇总以 `status=success` 为唯一成功口径，并另外报告题目总数、首次成功数、复测成功数、未生成图表数和各错误类别数量；终态完成率、SQL 生成率、图表展示率只能作为辅助指标。

## 产物

所有测试产物写入 `.codex-runtime`，使用本次日期和空间名区分：

- 两份 100 题 JSON。
- 两份逐题结果 JSON。
- 两份空间测试报告。
- 一份 200 题汇总报告。
- 一份推荐看板盘点和入口异常记录。
- 一份或两份“未生成图表问题”清单，至少包含题目、首次 attempt、record、SQL/数据信号、图表信号、页面证据和失败原因。

题目和结果 JSON 均需包含固定字段，确保后续可重新同步数据库状态或单独复测失败项。

## 错误与中断处理

- Redis、Worker 或 API 异常导致批量请求停滞时，暂停新提交，先完成四服务健康检查。
- 空间或数据源上下文不一致时，终止当前执行通道，重新进入正确空间后从未提交题目继续。
- 抽屉残留另一个空间的历史内容时，不继续混合提交；关闭旧请求并使用新会话验证上下文。
- 看板入口无内容或错误落页时，记录入口缺陷，并把题目配额分配给同空间其他有效推荐看板。
- 能力边界不自动算作产品运行失败，但不得计入 `success`；有完整 SQL 但无图表的问题必须进入未生成图表清单。

## 验收标准

1. `flam` 和`修仙`各有 100 个唯一问题及对应最终结果。
2. `flam` 题目来源中不包含“运营总览”入口及其内容。
3. 200 个问题均通过真实 AI 看板 UI 提交，不以接口直调替代。
4. 只有同一次尝试完整生成 SQL 且当前页面实际展示图表的题目才计入 `success`。
5. 所有 `has_sql_answer=true` 但没有展示图表的问题均进入未生成图表清单，不能被文本回答或完成状态覆盖。
6. 同一会话问题保持顺序，空间之间不存在数据源或回答串线。
7. 所有未完成和失败尝试都有复测结果或明确未解决原因。
8. 报告以 `status=success` 统计成功，不把有效文本、仅有数据或任务完成当作成功。
9. 题目、结果、复测、未生成图表清单和推荐看板盘点均可通过文件及数据库记录追溯。
