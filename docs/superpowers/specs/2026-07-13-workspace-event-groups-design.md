# 工作空间事件分组配置设计

## 背景

当前 `event_name_mappings` 同时承载完整事件参数字典和分析事件集合。First Zombie 字典种子脚本把支付流程、新手引导、活动参与等分析集合写入 `event_name_mappings`，并在冲突更新时整体替换原配置，导致正常导出的“事件参数对照”从 163 个事件、755 条参数缩减为 49 个事件、4 条参数。

本设计将“事件定义与参数”和“事件集合分组”拆成两类独立的工作空间元数据，避免分析口径再次覆盖埋点字典，并让业务人员通过 Excel 调整分组成员而不修改代码或 Data Skill。

## 目标

- 保持“事件参数对照”sheet 的格式、内容和维护职责不变。
- 新增工作空间级 `event_groups` 结构化配置，按当前工作空间和绑定数据源隔离。
- 新增固定 Excel sheet“事件分组”，支持分组导入导出。
- Data Skill 引用稳定的分组标识，运行时读取最新成员；修改分组成员不需要修改 Skill。
- 修正 First Zombie 种子脚本，禁止其继续用分析集合覆盖 `event_name_mappings`。
- 保持旧 Excel 兼容：没有“事件分组”sheet 时，不改变现有分组。

## 不做的事

- 首期不增加可视化事件分组编辑界面。
- 首期不在手动看板字段选择器中增加“整组事件”选择控件。
- 不把分组成员复制进 Data Skill 文本，也不把事件列表硬编码到通用 SQL 生成逻辑。
- 不改变“事件参数对照”的表头、参数展开规则或事件唯一性规则。
- 不通过空 sheet 隐式清空全部分组；清空能力留给后续独立、明确的操作。

## 方案选择

采用独立事件分组表，每个分组保存一条记录，成员事件按有序 JSONB 数组存储。

未采用的方案：

- 在现有 tracking 配置表增加 JSONB 字段：实现较快，但会继续扩大单行配置的覆盖风险，无法充分隔离事件字典与事件分组。
- 使用分组表和成员明细表两张关系表：约束最强，但首期只需整组读取和 Excel 整体替换，两表方案会增加不必要的迁移、CRUD 和事务复杂度。

## 数据模型

新增 `sys_tenant_tracking_event_group`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 雪花 ID |
| `tenant_id` | bigint | 当前工作空间边界 |
| `datasource_id` | bigint | 当前工作空间绑定的数据源 |
| `group_key` | varchar(128) | 稳定分组标识 |
| `group_name` | varchar(255) | 用户可修改的分组名称 |
| `description` | text | 分组业务说明 |
| `event_names` | jsonb | 有序、去重的事件名数组 |
| `sort_order` | integer | 分组展示顺序 |
| `enabled` | boolean | 是否启用 |
| 审计字段 | 与现有 tracking 表一致 | 创建人、更新人和时间 |

唯一约束为 `(tenant_id, datasource_id, group_key)`。所有读取和写入必须同时限定 `tenant_id` 与 `datasource_id`，不得跨工作空间或跨数据源合并同名分组。

`group_key` 使用稳定、可引用的 ASCII 标识，格式为 `^[a-z][a-z0-9_]{1,127}$`。修改 `group_name` 不改变 `group_key`，Data Skill 和语义上下文只使用 `group_key` 建立稳定引用。

修改 `group_key` 等同于删除旧分组并创建新分组，不属于普通重命名。若确需修改，引用旧标识的 Data Skill 必须同步调整；日常业务调整应只修改分组名称、说明或成员事件。

## Excel 设计

新增固定 sheet：`事件分组`。

| 表头 | 必填 | 说明 |
|---|---|---|
| 分组标识（必填） | 是 | 稳定 `group_key` |
| 分组名称（必填） | 是 | 用户可读名称 |
| 分组说明 | 否 | 业务范围和使用限制 |
| 分组排序 | 否 | 整数，默认 0 |
| 事件名（必填） | 是 | 必须存在于“事件参数对照” |
| 事件排序 | 否 | 同组内成员顺序，默认按行顺序 |
| 启用 | 否 | 是/否，默认是 |

每行表达一个“分组—事件”关系。导出时每行重复填写完整分组信息，不合并单元格，保证用户排序、筛选和复制后仍可独立解析。同一事件可以属于多个分组，同一分组中同一事件只能出现一次。

示例：

| 分组标识（必填） | 分组名称（必填） | 分组说明 | 分组排序 | 事件名（必填） | 事件排序 | 启用 |
|---|---|---|---:|---|---:|---|
| `payment_process` | 支付流程事件 | 只统计流程量 | 10 | `PayBuyRet` | 10 | 是 |
| `payment_process` | 支付流程事件 | 只统计流程量 | 10 | `PayFinish` | 20 | 是 |
| `onboarding` | 新手引导漏斗 | 新手步骤集合 | 20 | `EnterGame` | 10 | 是 |

## 导入语义

导入行为必须明确区分三种状态：

1. Excel 不包含“事件分组”sheet：不读取、不清空、不修改已有分组。
2. sheet 存在但只有表头或其余行全部为空：不修改已有分组。
3. sheet 至少包含一条有效数据：该 sheet 是当前工作空间和数据源的权威分组配置，校验通过后整体替换已有分组。

只要数据行包含任意非空内容，就必须进入校验；不能把字段缺失、格式错误或事件不存在的行当成“没有有效数据”后静默忽略。

“整体替换”只作用于事件分组表，不修改 `event_name_mappings`、字段配置、表配置或 Data Skill。

解析与保存必须在同一事务中完成。任一行校验失败时，整个事件分组更新失败，已有分组保持不变，不允许部分成功或静默跳过。

## 校验规则

- `group_key`、分组名称和事件名不能为空。
- `group_key` 必须符合格式约束。
- 同一 `group_key` 的名称、说明、分组排序和启用状态必须一致。
- 同一 `(group_key, event_name)` 重复出现时返回明确错误，不静默去重。
- 分组排序和事件排序必须为整数。
- 启用值只接受约定的布尔文本，不猜测无法识别的值。
- 每个事件名必须存在于当前工作空间的事件字典。

同一个 Excel 同时包含“事件参数对照”和“事件分组”时，先解析事件字典，再使用解析后的最终事件集合校验分组。两个配置通过全部校验后再一起提交。

如果只导入“事件参数对照”并删除了仍被现有分组引用的事件，导入必须失败并列出分组标识和缺失事件；系统不得自动删除分组成员，也不得留下悬空引用。用户可在同一 Excel 中同步更新“事件分组”后重新导入。

## 导出语义

- “事件参数对照”继续从 `event_name_mappings` 导出，现有内容和格式不变。
- “事件分组”从独立分组表导出。
- 新 sheet 放在“事件参数对照”之后、物理表 sheet 之前。
- 没有事件分组时仍导出只有表头的空 sheet，便于用户新增配置；再次导入该空 sheet 不修改数据库。

## 后端接口与 DTO

在 tracking 配置聚合 DTO 中新增 `event_groups` 只读/写入字段，使同一配置服务能够返回当前工作空间和数据源的事件字典及事件分组，但两者使用不同的持久化仓储和保存逻辑。

事件分组对象至少包含：

```json
{
  "group_key": "payment_process",
  "group_name": "支付流程事件",
  "description": "只统计流程量",
  "event_names": ["PayBuyRet", "PayFinish"],
  "sort_order": 10,
  "enabled": true
}
```

权限、租户和数据源校验复用现有 tracking 配置服务。不得仅凭请求参数读取其他工作空间的分组，也不得根据相似数据源名称回退到其他配置。

## Data Skill 与语义上下文

Data Skill 负责描述业务口径，例如“真实交易”和“支付流程量”的区别；事件分组负责保存可变的成员列表。Skill 只引用稳定 `group_key`，不重复保存具体事件名。

构建 datasource-scoped 语义上下文时，后端将当前启用的事件分组作为独立结构化区块注入，包含 `group_key`、名称、说明和成员事件。SQL 生成只能使用当前工作空间、当前已授权数据源中的分组。

修改分组成员、显示名称或排序不需要修改 Data Skill。只有分组业务含义、指标公式、分母、时间窗口等口径发生变化时，才需要修改 Skill。

首期不要求前端提供分组编辑器，也不把事件分组作为手动看板中的新字段类型；Excel 是首期唯一写入入口。

## 种子与迁移策略

First Zombie 修复分为一次性迁移和长期防护：

1. 对当前系统库 tracking 配置和分组表执行备份。
2. 将现有 13 个分析集合迁移为独立事件分组记录。
3. 使用业务确认的正常 tracking Excel 恢复完整 `event_name_mappings`。
4. 校验所有迁移后的分组成员均存在于恢复后的事件字典；缺失项必须人工确认，不自动删除或改名。
5. 更新 First Zombie tracking 种子脚本，移除对完整 `event_name_mappings` 的覆盖。

普通种子脚本不写入事件分组，避免未经业务确认的默认成员与当前权威事件字典冲突。只有显式使用 `--seed-event-groups` 时，脚本才先校验所有默认成员均存在于当前事件字典，再以 `ON CONFLICT DO NOTHING` 创建缺失分组；任一事件缺失时整次分组初始化失败。普通 seed 执行不得更新或清空用户维护的事件字典和事件分组。

## 错误处理

导入错误必须定位到 sheet、行号、分组标识和事件名，例如：

```text
事件分组 sheet 第 8 行：事件 PayFinish2 不存在于当前事件参数字典，未更新任何事件分组。
```

对于只导入事件字典导致的悬空引用，应返回：

```text
事件 PayFinish 仍被分组 payment_process 引用；请在同一 Excel 的“事件分组”中同步调整后重新导入。
```

数据库写入异常必须回滚整个分组替换事务，不影响原事件字典和原分组配置。

## 测试策略

### 数据模型

- 唯一约束覆盖同工作空间、同数据源、同 `group_key`。
- 不同工作空间或数据源可以使用相同 `group_key`，数据互不可见。

### Excel 导出

- 工作簿新增“事件分组”sheet，表头和顺序固定。
- 一个分组的多事件按多行完整输出，不合并单元格。
- “事件参数对照”的表头、行数、参数和合并规则保持原行为。

### Excel 导入

- 缺少 sheet 时保留已有分组。
- 空 sheet 时保留已有分组。
- 有效 sheet 整体替换当前分组。
- 同一事件属于多个分组时导入成功。
- 重复成员、冲突分组信息、非法排序、非法布尔值和未知事件均阻止整个更新。
- 同时导入事件字典与分组时按最终事件集合校验。
- 删除仍被现有分组引用的事件时阻止事件字典更新。

### 语义上下文

- 只注入当前工作空间、当前授权数据源的启用分组。
- 修改分组成员后，下一次语义上下文立即使用新成员，无需修改 Data Skill。
- 禁用分组不进入可用语义上下文。

### 种子回归

- 重复运行普通 First Zombie seed 不覆盖用户事件字典。
- 重复运行普通 seed 不覆盖用户修改过的同名分组。
- 迁移前后完整事件参数数量和内容可对账。

## 验收标准

- 正常 tracking Excel 的“事件参数对照”可原样恢复并再次导出，内容不被分析分组替换。
- 导出文件新增“事件分组”sheet，能够无损往返导入导出。
- 修改分组成员后无需修改代码或 Data Skill，新的语义请求即可读取最新成员。
- 旧 Excel、缺少分组 sheet 的 Excel和空分组 sheet 均不会改变已有分组。
- 任何非法或悬空事件引用都产生明确错误，不发生静默删除、替代或部分保存。
- First Zombie 普通种子脚本不再覆盖用户维护的事件字典或事件分组。
