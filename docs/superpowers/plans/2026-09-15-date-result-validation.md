## 已确认的根因

记录 6587 查询范围为 2026-09-08 至 2026-09-14。SQL 的 calendar.dt 由 `DATE_FORMAT(..., '%Y%m%d')` 转为整数，最终却使用 `STR_TO_DATE(CAST(c.dt AS CHAR), '%Y-%m-%d')`。查询返回七行指标，但横轴日期全部为 NULL，图表将这些点绘制在同一空横坐标上。

日志证明日期规则已经传入模型，生成 SQL 仍违反规则。问题不是缺少七天数据，而是生成后的 SQL 和返回结果缺少执行校验。

## SQL 校验与 LLM 修复

- `common/utils/sql_date_validation.py` 使用 SQLGlot 作用域追踪明确的 DATE_FORMAT、有效日期字面量、CAST、DATE、CTE、子查询、别名和同格式 UNION。
- 对已知 CTE 的 `*` 和 `table.*` 转发保留来源。混合格式、未知表达式、物理表星号或未实现列合并语义的 USING/NATURAL JOIN 星号保持未知，不按位置猜字段。
- `apps/datasource/crud/sql_date_metadata.py` 读取当前租户、数据源、已启用跟踪配置及授权物理字段的结构化 encoding，不读取其他工作空间或未授权字段。
- 仅当输入编码与解析格式明确冲突时抛出专用错误，包含错误表达式、实际格式和期待格式。不是对 SQL 做全局字符串替换。
- SmartQA 将错误和原 SQL 送入已有 LLM 修复流程；修复后重新经过准备、权限检查和执行。保留原最多两次 SQL 修复预算。
- 分析助手预执行错误接入原有一次定向修复。看板及其他共享执行入口使用相同确定性校验，不另建无限重试机制。
- 本次格式冲突检查适用于现有 MySQL 兼容类型，明确比较 `%Y%m%d` 与 `%Y-%m-%d`。不声称已将所有自然语言 Data Skills 或所有数据库日期函数转换成可执行约束。

## 结果、历史图表与导出

- SmartQA 在保存查询成功数据前检查趋势查询中可识别的单一日期投影；多日期投影暂不猜测横轴，待图表绑定后检查真实横轴。
- 日期为空或无效但不能证明 SQL 错误时，明确报错并停止自动改写。不会补猜日期、丢弃坏行或替换字段。
- 图表保存前检查实际横轴；辅助日期列允许 NULL。纯 TIME 值不按完整日期解析；空结果、合法指标 NULL、零值和同日多系列保持原语义。
- 前端共享 BaseChart 拦截折线图/面积图空横轴，ChartInsightHeader 同步隐藏误导性趋势摘要，ChartBlock 阻止将这种无效图表添加到看板。
- 历史回显、全屏和看板使用共享渲染保护；读取历史不会自动调用模型或修改数据库。原始 SQL/表格继续由原有入口提供。
- 后端图片输出在请求图片服务前执行相同横轴检查。原始表格导出不伪造日期。
