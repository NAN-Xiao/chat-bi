## 修复内容

### 1. 公式原子指标筛选的请求结构不正确

页面中 `metric.filters` 是编辑状态数组，`filterLogic` 另行存放。原序列化直接提交数组，导致添加非空条件后被结构化条件校验拒绝，实际错误为 `formulaMetrics[0].tokens[1].metric.filters` 格式无效。

修复 `formulaMetricUtils.ts` 的请求序列化：显式输出 `{logic, rules}`，递归保留嵌套组和字段解析。编辑状态与保存状态仍使用原来的数组，序列化不修改用户草稿。没有增加后端数组兼容兜底或跳过校验。

### 2. 非数值 MIN/MAX 可进入算术公式

授权的文本 MIN/MAX 独立展示是合法的，但原计划没有记录其结果类型；用于加法等公式后，PostgreSQL 实际报 `text + integer` 不存在。

现在按服务端元数据和聚合方式确定结果是否为数值，再统一校验公式引用。普通指标引用与公式内部原子指标都受到保护；文本 MIN/MAX 独立展示继续有效，文本字段的 COUNT DISTINCT 仍可参与公式。

### 3. JSON 条件的等价括号被错误拒绝

真实前端序列化接入后，PostgreSQL JSON 数值过滤在 SQL 校验阶段被误报“事实筛选与配置不一致”。原因是 lineage 展开去掉了语法括号，预期表达式仍保留函数参数括号。

修复共享表达式规范化：根据 AST 运算树重新构造括号比较，统一等价函数参数表达式，同时确保 `a*(b+c)` 与 `(a*b)+c` 仍不相等。补测 OR/AND 分组不可被弱化；相关漏斗、间隔校验测试一并回归。

另修复公式前端测试的模板读取路径：表单已经拆到 `DashboardAnalysisModelForm.vue`，旧测试仍只检查父文件。本次未改动页面布局或增加控件。
