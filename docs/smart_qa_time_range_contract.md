# Smart Q&A 时间范围契约

## 背景

Smart Q&A 曾出现模型已生成正确月份范围，但后端重新解析用户问题失败后，将范围覆盖成默认最近 7 天的问题，造成标题、日期配置和最终 SQL 不一致。

修复目标是让时间语义只由现有 SQL 生成 LLM 调用理解一次。后端不再枚举解析“八月份”“上周”“过去 30 天”等自然语言，只校验模型返回的具体日期并按字段类型渲染 SQL。

## 适用范围

- 本契约只作用于已启用看板日期参数能力的 Smart Q&A 工作空间。
- 示例工作空间继续沿用现有租户排除配置，不要求 `time_scope`、`time_range` 或 dashboard 日期 token，不改变其现有 SQL 行为。
- 不查询数据源最大业务日期。
- 不增加正常请求的 LLM 调用次数。

## 流程

```text
后端计算系统业务日期
        |
        v
注入现有 SQL 生成提示词
        |
        v
同一次 LLM 调用返回具体日期、date_filter 和 SQL 模板
        |
        v
后端校验日期契约和系统业务日期上限
        |
        v
按字段类型渲染并执行 SQL
```

系统业务日期根据 `settings.DASHBOARD_BUSINESS_TIMEZONE` 计算，并以 `YYYY-MM-DD` 注入提示词。它是相对时间的唯一参考日期。

## LLM 返回协议

所有非 `metric` 图表必须返回：

```json
{
  "success": true,
  "time_scope": "explicit",
  "time_range": {
    "start_date": "2026-08-10",
    "end_date": "2026-08-16"
  },
  "date_filter": {
    "time_field": "dt",
    "date_parameter_type": "yyyymmdd_number",
    "date_expression": {
      "version": 1,
      "mode": "range",
      "start": {"mode": "static", "date": "2026-08-10"},
      "end": {"mode": "static", "date": "2026-08-16"}
    }
  },
  "sql": "SELECT ... WHERE dt BETWEEN {{dashboard_start_yyyymmdd}} AND {{dashboard_end_yyyymmdd}}"
}
```

约束：

- `time_scope` 只能是 `explicit` 或 `unspecified`。
- 相对时间也必须直接返回具体 `start_date/end_date`，不得只返回 `unit/offset`。
- `time_range` 与 `date_expression` 必须完全一致。
- 结束日期不得晚于系统业务日期。
- SQL 必须使用与 `date_parameter_type` 匹配的 dashboard 日期 token。
- 明确时间不得被默认七天覆盖。

## 默认七天

用户完全没有表达时间时，`time_scope=unspecified`，具体范围必须是系统业务日期之前最近 7 个完整自然日，不含系统业务日期。

系统业务日期为 `2026-08-19` 时：

```json
{
  "time_scope": "unspecified",
  "time_range": {
    "start_date": "2026-08-12",
    "end_date": "2026-08-18"
  }
}
```

后端验证该范围必须严格等于默认七天，不能落入旧的 14 天默认路径。

## `yyyymmdd` 渲染

LLM JSON 内统一使用 ISO 日期，执行 SQL 按字段类型渲染。

`yyyymmdd_number`：

```sql
WHERE dt BETWEEN 20260810 AND 20260816
```

`yyyymmdd_text`：

```sql
WHERE dt BETWEEN '20260810' AND '20260816'
```

不能把整数分区渲染成带引号的 ISO 日期，也不能把文本分区渲染成裸数字。`date` 和 `timestamp` 按已有方言渲染规则处理。

## 后端错误

以下情况均进入已有日期配置修复流程，不得静默使用默认范围：

- `missing_time_scope`
- `missing_time_range`
- `invalid_time_range`
- `time_range_exceeds_business_date`
- `invalid_default_time_range`
- `time_range_mismatch`
- `sql_time_range_mismatch`

## 验收标准

```text
LLM 返回的具体日期
= date_expression 的静态日期
= 保存 SQL 模板代表的日期范围
= 最终执行 SQL 的日期范围
```

回归用例至少覆盖上周、过去 30 天、八月份、具体日期范围、无时间默认七天、超过系统业务日期、缺少具体日期、`yyyymmdd_number`、`yyyymmdd_text`，以及示例工作空间不受影响。

## 本次在线验收

验收日期：`2026-08-19`。模型：当前默认在线模型 `qwen3.5-plus`。

逐条使用实际 SQL 生成提示词调用模型，并依次验证：

1. 模型返回的 `time_range` 等于预期具体日期。
2. SQL 中的日期条件可转换为成对 dashboard token。
3. 后端具体日期契约校验通过。
4. 执行 SQL 渲染出的 `yyyymmdd` 起止值与 `time_range` 一致。

覆盖表达：近 3/7/14/21/30/45/60/90 天、昨天、前天、本周、上周、本月、上月、8 月 1 日到昨天；另验证今天趋势、实时趋势、今天实时趋势和实时汇总。

日期范围语义验收结果：`15/15` 通过。实时专项首次发现“实时”被误套默认七天；补充实时提示、当前业务日校验和 timestamp 半开区间改写后，“今天的付费情况”“实时付费情况”“实时付费趋势”在线复测 `3/3` 通过。
