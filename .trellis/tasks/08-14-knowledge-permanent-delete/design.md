# 技术设计：知识库永久删除与文件清理

## 边界与接口

- 保留 `DELETE /knowledge-base/{id}` 的现有“未发布硬删、已发布归档”语义。
- 新增 `DELETE /knowledge-base/{id}/permanent`，仅处理 V2 已归档知识库。
- 前端 API 增加 `permanentDelete(id)`；已归档行和详情调用同一方法。
- 服务层新增明确的永久删除方法，不在 API 路由中拼接删除 SQL。

## 数据删除顺序

1. 按租户和知识库 ID 锁定主记录并执行现有 `require_manage` 权限检查。
2. 要求 `archived=true`，否则返回 `KNOWLEDGE_PERMANENT_DELETE_REQUIRES_ARCHIVE`。
3. 收集 `knowledge_base.file_id` 与全部 `knowledge_base_version.file_id` 的非空去重集合。
4. 删除该知识库的 `knowledge_publish_job`，解除版本上的 `RESTRICT` 外键。
5. 删除所有版本；数据库级联删除切片、适用性、来源引用、语义对象引用及其解析结果。
6. 删除知识库主记录；数据库级联删除工作空间覆盖配置。
7. 提交数据库事务后逐个检查候选文件是否仍被 `knowledge_base` 或 `knowledge_base_version` 引用，只回收无引用文件。

## 文件安全

- 文件引用判断由知识库模块的单一 helper 负责，V2 永久删除、未发布硬删和草稿文件替换共用。
- 文件清理发生在数据库提交之后，避免事务回滚后数据库仍引用已经删除的文件。
- `missing_ok` 表示文件已达到清理结果；真实 I/O 失败写日志并返回结构化统计。
- 回滚草稿可能复用历史版本的同一 `file_id`；引用检查必须跨所有知识库版本，禁止按知识库局部判断后直接删除。
- 上传解析失败或 CAS 冲突继续只删除本次暂存文件，不触碰原文件。

## 前端交互

- 当前列表保持现有操作，已归档列表的行操作为“查看、下载、恢复、永久删除”。
- 永久删除使用输入确认，输入值必须与知识库名称完全一致。
- 成功后关闭正在查看的对应抽屉、刷新已归档列表，并提示删除结果。
- 如果后端报告物理文件清理失败，提示“知识库已删除，部分源文件清理失败”，避免让用户误以为数据库删除也失败。

## 兼容与回滚

- 不修改数据库结构和旧版路由，回滚代码即可移除新入口。
- 永久删除本身不可回滚，因此只允许从已归档状态进入，并由前端名称确认和后端状态校验双重保护。
- 自动保留期清理延后到具备后台调度、审计和可配置保留期后再设计。
