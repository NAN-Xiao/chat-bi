# 技术设计：知识库版本保留上限

## 责任边界

- `KnowledgeVersionRepository` 负责在已持有知识库行锁的事务内选择和删除超限版本，并返回待检查的源文件 ID。
- 版本 API 的共享提交函数在普通创建草稿和回滚生成草稿两个用户入口统一触发保留策略，并在事务提交后调用现有 `cleanup_unreferenced_source_files`。
- `KnowledgeLifecycleService` 继续只负责状态机；后台 backfill 只为知识库创建初始版本，不进入历史裁剪路径。
- 版本列表继续只读取真实记录，不用前端切片或后端 `LIMIT 10` 掩盖未清理数据。

## 保留算法

1. 知识库行先由生命周期服务 `FOR UPDATE` 锁定，仓储裁剪前再次确认并持有同一行锁。
2. 创建并刷新新版本，更新 `draft_version_id`。
3. 查询同一租户、同一知识库的所有版本，按 `version_number DESC` 排序。
4. 建立保护集合：三个版本指针，以及状态为 `QUEUING`、`QUEUED`、`RUNNING` 的发布任务所引用版本。
5. 先保留保护集合，再按版本号从新到旧补足到 10 个；其余版本为删除候选。
6. 收集候选的非空 `file_id`，按候选版本 ID 删除发布任务，再删除版本。
7. 事务提交后执行全局文件引用检查，仅删除无引用文件。

有效状态下三个指针与活动任务都指向最新版本，因此结果就是最近 10 个版本。保护集合优先只用于防止异常或并发状态下误删仍参与业务流程的版本。

## 数据与并发

- 保留计算和版本创建共用知识库行锁及事务，两个并发创建请求不能基于同一旧集合分别裁剪。
- 删除条件同时包含 `tenant_id`、`knowledge_base_id` 和明确的版本 ID 集合。
- 发布任务必须显式先删，其他已建模的版本派生表依赖数据库 `ON DELETE CASCADE`。
- `next_version_number` 继续取现存最大值加一。由于只删除最旧版本，最大版本号始终保留，编号不会回退。

## 文件清理

- 数据库删除返回候选 `file_id`，不在仓储事务内直接操作文件。
- API 提交成功后调用 `cleanup_unreferenced_source_files`；该 helper 会同时检查所有 `knowledge_base_version.file_id` 和 `knowledge_base.file_id`。
- 清理失败只记录结构化日志，避免将已提交的版本创建误报为失败。

## 存量与回滚

- 当前 `zhishu_bi_2.0.0` 数据库不存在超过 10 个版本的知识库，不新增破坏性迁移。
- 部署后所有新增版本路径都会维持上限；若其他环境已存在超限数据，下一次创建或回滚版本时会在同一规则下收敛。
- 代码回滚不会恢复已经物理删除的版本；这是用户明确接受的产品行为。

## 兼容性

- 不修改数据库结构和 HTTP 响应结构。
- 不改变当前版本检索过滤条件，也不改变保留版本的下载、回滚与恢复语义。
- 不删除知识库级主文件引用；是否回收完全由全局引用检查决定。
